### ⚠️ MariaDB crash recovery — read this before "fixing" a startup failure

XAMPP's panel says only *"MySQL shutdown unexpectedly… may be due to a blocked port"*, which is almost never the reason. **The message is useless; the log is not.** Two different real causes have hit this machine:

- **2026-09-03 — crashed Aria system tables** (`mysql.proxies_priv`, `mysql.db`, `mysql.proc`). They are **Aria** (`.MAD`/`.MAI`), so `myisamchk` does nothing; `aria_chk --safe-recover` on a stopped server is the tool. **Now prevented**: `my.ini` sets `aria_recover_options=BACKUP,FORCE` (was `BACKUP,QUICK`, which checked but never repaired), so the server repairs them at startup instead of aborting.
- **2026-09-09 — InnoDB `LSN in the future`** → `invalid undo header offset 0` → `Plugin 'InnoDB' registration as a STORAGE ENGINE failed`. The data pages were at LSN ~77 M while the redo log was at ~73.5 M, i.e. **the redo log was older than the data**. This is *not* repairable in place: `innodb_force_recovery` 1–4 all failed, only **5** started the server. The fix is always the same three steps — **force-recover → `mysqldump` → rebuild the datadir → import**.

Rules that came out of the second incident, all load-bearing:

- ⚠️ **Never delete `ib_logfile*` to make the server start.** That is the top forum advice and it is exactly what *creates* "LSN in the future": a fresh log begins at a low LSN while the pages keep their real, higher one.
- ⚠️ **Never rebuild a datadir from `C:\xampp\mysql\backup`.** That folder is XAMPP's shipped "pristine" copy from **2019 and it is internally inconsistent** — its `ib_logfile1` is 78 minutes older than its `ibdata1`, and its log checkpoint sits at LSN ~300 k while its own pages are past 4.7 M. A datadir built from it *appears* to work and then aborts with the same error the moment anything makes InnoDB re-derive the system LSN. Use **`mysql_install_db.exe --datadir=… --port=3306`** instead; it produces a genuinely self-consistent datadir (0 errors, 0 "in the future" in the log).
- ⚠️ **Changing `innodb_log_file_size` is a destructive operation.** The startup resize deletes `ib_logfile*` and re-derives the LSN from the checkpoint — on an already-inconsistent datadir it *is* the trigger. `my.ini` therefore pins **48M, the exact size `mysql_install_db` creates**, so the server never resizes on boot. Take a dump before ever touching that number.
- ⚠️ **The data lives in the dumps, not in the datadir.** Rebuilding takes about a minute *if* a recent `mysqldump` exists; on 2026-09-09 the newest committed one was a week old. Hence the scheduled task above — and `backend/mediary_backup.sql` should be refreshed after significant data changes.
- ⚠️ **The system schemas are never restored from a copy** — `mysql_install_db` rebuilds them and the user DBs come back from `mysqldump`. Only `pma`@`localhost` has to be recreated by hand (`GRANT SELECT, INSERT, UPDATE, DELETE ON \`phpmyadmin\`.*`); `root` at `localhost`/`127.0.0.1`/`::1` (no password) is created by the bootstrap.
- ⚠️ **`count(*)` lies under `innodb_force_recovery` ≥ 4.** That level skips the change-buffer merge, so a secondary index can read back empty. Confirm with `force index (PRIMARY)` and `CHECK TABLE` before concluding a table lost its rows.
- ⚠️ **Georgian in `mysql.exe -e "…"` is mangled to `?` by the Windows console** (the same trap as `tinker`/curl argv). Verify Georgian text through `php artisan tinker`, not through a `REGEXP '[ა-ჰ]'` on the command line.
- 🟡 **Still to do, needs an elevated shell (see the session note):** install MariaDB as a **Windows service** so the OS stops it cleanly on shutdown/logoff. Every unclean kill is a crash-recovery cycle, and that is what wears the datadir down in the first place.

Normally the scheduler runs it every minute; start it with **`php artisan schedule:work`** (or a Windows Task Scheduler entry calling `schedule:run`). ⚠️ Without it the browser channel still works — the SPA's polling calls the same dispatcher — but Telegram/email only go out while the app is open.

- `php artisan tinker` — REPL. **Georgian text: pass via heredoc (stdin), never via curl `-d` args** — the Windows console mangles UTF-8 in argv to `?`.

Frontend (`frontend/`):

## Architecture

**Data model** (`backend/app/Models`): `Movie` and `Series` are parallel domains. Both link to shared `Genre` / `CastMember` via **polymorphic** pivots `genreables` / `castables` (morph aliases `movie`/`series` registered in `AppServiceProvider::enforceMorphMap`; pivot carries `character`, `billing_order`). Bilingual text lives in per-entity translation tables (`movie_translations`, `series_translations`) surfaced via accessors (`title_ka`/`title_en`, `description_ka`/`description_en`) so the API shape stays flat; genres/cast have their own translation tables. `cast_members.gender` mirrors TMDB's coding (1=female, 2=male, 0/3=unspecified) and drives the gallery's female/male cast filters (§10); it is null on records synced before 2026-09-03 and is backfilled on demand. **`status` is a per-user dictionary row since 2026-09-12** (`status_id` → `statuses`, §6.4 — see *Statuses* below; the old enum column is gone); `is_favorite`; `sync_status`. **Movies have franchise/collection** (`tmdb_collection_id`, `franchise_next` badge, clustering); **series do not** (TMDB TV has no `belongs_to_collection`) but add `seasons`/`episodes`. **`Anime` is the third domain, live since 2026-09-11** (§7.1) — its own `animes`/`anime_translations` tables, controller, policy, resource and enricher, but the *shared* `genres`/`cast_members` under morph alias `anime`. ⚠️ **The set of TMDB-backed domains is one map, `App\Support\MediaDomain`** (`TYPES`, `TV_TYPES`, `castRelation()` — `movies`/`series`/`animes`, model/enricher lookup): `['movie', 'series']` used to be written out in fourteen places — validation, sync, gallery, the console command, route `whereIn` — and missing one is silent (a 422, or a domain quietly dropped from a plan). **Route-level code splitting (Tasks §4, 2026-09-12)** — `App.tsx` imported all 37 pages statically, so every visitor downloaded the whole app: one **1,697 kB** chunk. The pages are `lazy()` now with a `<Suspense>` inside `<main>`, and the initial payload is **862 kB across 40 chunks** (79 → 40 after the fix below). Four things are easy to get wrong:
- ⚠️ **One static import from a non-page module undoes the whole thing.** `Sidebar.tsx` imported `GALLERY_CUTS` from `pages/GalleryPage`, which dragged the gallery page — and with it the lightbox (`photo-grid`, 57 kB), `react-select` (`selectStyles`, 81 kB), the date picker (78 kB) and `WebVideoDialog` (34 kB) — into the **initial** graph. The list now lives in **`lib/galleryCuts.ts`**, which both sides import, so there is still exactly one copy. **Check `grep "from '@/pages/" src/components src/lib` after touching this**: a single hit is worth hundreds of kB.
- ⚠️ **`Suspense` sits inside `<main>`, not around the whole shell** — the header, sidebar and **the player** must stay mounted while a page chunk loads; a full-screen fallback would have made every navigation look like a cold start (and `PlayerBar` lives outside `<Routes>` precisely so playback survives navigation).
- ⚠️ **The `.then((m) => ({ default: m.X }))` is written out 37 times on purpose.** The pages use named exports, and a generic `lazyPage(load, name)` helper loses the props type — `<LibraryPage type={type} />` would stop being checked, which is the one thing `tsc` is here for.
- ⚠️ **There is no error boundary around the lazy routes yet**: if a chunk fails to load (a stale deployment, a dropped connection) React unmounts to a blank page. Acceptable on a local dev machine, and the first thing to add if this app is ever hosted.

**Frontend tests (Tasks §3, added 2026-09-12)** — the SPA had **none**: `tsc -b` and oxlint check types and style, so every behavioural rule in `lib/` was unverified. Vitest + jsdom now run `src/**/*.test.ts` (`npm test`), and the scope is deliberate — **`lib/`'s pure functions, not components**: `embed` (the iframe allowlist and the three players' event decoder), `tags` (`dedupeTags`, the twin of `Video::normalizeTags()` — the two sides must count identically or the form shows one thing and the database stores another), `statuses` (name fallback, `statusByKey`, and `statusTone`'s role fallback), `dates` (the `sv-SE` rule — `toISOString()` shows yesterday during Tbilisi's night hours) and `paged` (`{data, meta}` vs. `all=1`'s bare `{data}`). ⚠️ **The config is its own `vitest.config.ts`, not a `test` block in `vite.config.ts`** — the app config loads the React and Tailwind plugins, which pure-function tests never need. ⚠️ **jsdom is load-bearing, not comfort**: `playableEmbedSrc()` reads `window.location.origin` for YouTube, i.e. the one case `enablejsapi`/`origin` exists for could not be tested in node at all. ⚠️ **`useDragReorder`'s `moveBy()` is still untested** — it lives inside a hook, so it needs `@testing-library/react`; that dependency was not added for one function.

**List pagination (built 2026-09-12)** — every module's `index()` used to end in `->get()`, so opening a section shipped the whole library: measured on the real 353-movie database, `GET /api/movies` was **806 kB**, now **109 kB**. The single definition is **`Controller::paginated($request, $source)`** — `page`/`per_page` (default 60, capped at 500) — and every one of the ten list endpoints (`movie` · `series` · `anime` · `video` · `song` · `book` · `board_game` · `game` · `note` · `bookmark`) goes through it. Seven things are easy to get wrong:
- ⚠️ **`all=1` is an explicit escape with exactly four callers** — `/purge`'s queue and tag pool, bulk status/type change, `MediaRecordPicker`/`GenreItemsManager`'s record pools, and the playlist's song pool. Those build a *scope*, so a page-2 record silently missing from the list would make the resulting delete or bulk edit wrong. Using it on a grid re-creates the problem this fixed.
- ⚠️ **The base-class constants are `LIST_PER_PAGE`/`LIST_PER_PAGE_MAX`, not `PER_PAGE`/`MAX_PER_PAGE`.** `GalleryController` already had a `private const MAX_PER_PAGE`, and narrowing an inherited constant's visibility is a **PHP fatal** — the whole suite died with "Premature end of PHP process" until the base names moved out of the way. A generic name in a base class squats on every child.
- ⚠️ **The frontend model is "one page that grows": `page` is always 1 and `per_page` increases** (`lib/paged.ts` — `useListLimit`, `readPage`, `PAGE_SIZE`; the button is `ui/show-more.tsx`). Real page-2 fetches would break the two things that compute over the *loaded prefix*: `MovieGrid`'s section grouping (`defaultGrouping`) and the franchise cluster, whose per-section totals would stop matching the list.
- ⚠️ **Movies cluster franchises inside the page**, which is only correct *because* the client always loads a prefix. `annotateFranchise()` computes the badge with its own query, so it works on any subset; `clusterByFranchise()` does not, and a real page 2 would split a collection across pages.
- ⚠️ **`all=1` returns no `meta`** (a whole list is not a page), so `readPage()` falls back to the array's own length — otherwise "show more" would sit there forever on a list that is already complete.
- ⚠️ **The player queue is still the *whole* filtered list**, not the loaded page: pressing play fetches `all=1` once (cached, and only on the explicit click) so a 500-song filter does not stop at 60. That rule predates pagination and deliberately survives it.
- ⚠️ **`paginated()` accepts a `Collection` as well as a query builder.** `VideoSearch::search()` ranks in PHP, so SQL can no longer take the `limit`; without that branch the one endpoint that most needs cutting would have stayed unbounded. `LibraryPage` keeps its numbered pager for `libraryPageSize > 0` and asks the server for the prefix covering the current page; at `0` (the default) it is one growing list.

**Statuses (Tasks §6.2/§6.4, built 2026-09-12)** — a record's status is a **per-user dictionary row**, not an enum. One table, `statuses` (`user_id`, `module`, `key`, `name_ka`/`name_en`, **`role`**, `icon`, `color`, `is_default`, `sort_order`), and `status_id` on `movies` · `series` · `animes` · `videos` · `note_entries` · `bookmarks`. The registry is `App\Support\StatusDomain` (domain → model + module + defaults), the behaviour is `Concerns\HasStatus`, and **one** controller serves all six (`GET|POST /api/statuses/{domain}`, `PUT|PATCH|DELETE /api/statuses/{domain}/{id}`, `POST .../reorder` — the `/visibility/{domain}` pattern). Frontend: `api/statuses.ts` + `lib/statuses.ts` (`useStatuses` / `useStatusMap` / `useMergedStatuses` / `statusName` / `statusTone`), the editor is a row in `lib/dictionaries.tsx` (`/dictionaries/<domain>-statuses`), and `components/StatusDialog.tsx` is its form. Thirteen things are easy to get wrong:
- ⚠️ **`role` (`todo`/`doing`/`done`) is the whole reason this works.** Three places ask for *meaning*, not for a name: `MatchService` ("we both watched it"), `PurgeService` and the franchise badge. A user-typed name can't answer that (my „ნანახი" and your „ვნახე" are the same thing) and neither can an id (it's per-user) — without the column all three would fail **silently**. It is therefore required on create and never nullable.
- ⚠️ **Book, game and board game deliberately keep their enum** (the user's list). So both mechanisms are live at once and every "is this done / what statuses exist" question goes through one function — `PublicDomain::isDone()` / `PurgeService::statusesFor()` — never through an inline `if`.
- ⚠️ **The old `status` column was dropped, not kept alongside.** Two sources for one fact drift (the `hltb_*` and `Book::syncProgress()` trap). The migration therefore maps values → dictionary rows **first** and drops the column after.
- ⚠️ **`status` indexes must be dropped before the column**, and the migration reads them **out of the schema** (`Schema::getIndexes`) instead of naming them: `status` took part in three different indexes (`status`, `user_id+status`, `visibility+status`) and sqlite refuses to drop an indexed column. Hand-written names missed `movies_visibility_status_index` on the first run. Each one is rebuilt on `status_id`.
- ⚠️ **The API returns an object, not a string** (`{id, key, role, name_ka, name_en, icon, color}` or `null`) — including in `PublicDomain::card()`. The name lives in the **owner's** dictionary, so a stranger reading a public profile could not resolve a bare key; returning both separately would state one fact twice. `StatusResource::brief()` is the single shape.
- ⚠️ **`key` never changes.** Renaming edits `name_*`; the key is what ties the dictionary to old links (`?view=watched`), to `StatusDomain`'s defaults and to `PurgeService::TARGET_STATUSES`.
- ⚠️ **The relation ignores the `owner` scope** (`belongsTo(Status::class)->withoutGlobalScope('owner')`). `Status` uses `BelongsToUser`, so on a public profile or a match the other side's status would come back **empty** — the card would lose its badge and "both watched" would always be zero. The row is only reachable through `status_id` on an already-filtered record.
- ⚠️ **`$with = ['status']` on all six models.** Every list needs the badge, the filter and the role; a per-call `with()` would be forgotten in one of twenty places.
- ⚠️ **Defaults are seeded lazily and with the query builder, not `create()`** (`Status::ensureDefaults`). Lazy because a module can be enabled later (`VideoType::ensureDefaults`'s rule); query builder because the seed is written by the machine — through the model it would fire `AuditObserver` and the first page load would bury the log under twenty "status created" rows.
- ⚠️ **`AuditLogger` writes the status *key*, never `status_id`.** "3 → 4" is unreadable, and deleting the dictionary row would destroy the answer entirely — the same reason `subject_label` is stored as a copy.
- ⚠️ **Everything is deletable, including the last status and the default.** A record without a status is legal (`status_id = null`); deleting the default promotes the next row, or new records would silently get none. Deleting with `move_to` reassigns, exactly like every other dictionary.
- ⚠️ **`video` has a status now** — it had none before. That adds `PATCH /api/videos/{video}/status`, `POST /api/videos/bulk-status`, a `status` entry in `FieldCatalog`, sidebar sections and a `status` mode in `PurgeService::TARGET_MODES` (and in the frontend mirror `PURGE_TARGET_MODES`, whose `satisfies` types then force `PurgePage`'s maps to keep up). Its `MatchService` `both_done` is a number now, not `null`.
- ⚠️ **`watched_at` is set from the role, not the name** (`HasStatus::applyStatusKey()` — the single write point). ⚠️ Video, note and bookmark override `statusDoneColumn()` to `null`: a video's `watched_at` is a *playback* timestamp (`POST /videos/{id}/watched`), a different fact, and one column holding two facts is the trap `Book::syncProgress()` fights.
⚠️ **The i18n keys `status.*`, `notes.statuses.*` and `bookmarks.statuses.*` are gone** — those names live in the database now, and a fixed translation key would render a renamed status under its old label. `books.statuses.*` / `games.statuses.*` / `boardGames.statuses.*` stay, because those three are still enums. The new namespace is **`statuses.*`** (dictionary chrome: titles, roles, "default").

**Roles & permissions (Tasks 1.6)** — `roles` table (`key`, names ka/en, `permissions` JSON, `is_system`) + `users.role_id`; the old `users.role` enum is **gone**. A permission is **module-internal CRUD** (`view`/`create`/`update`/`delete`), while *access* to a module stays in `module_user` — two separate mechanisms. `permissions` shape: `{"movie":["view","update"],"*":["view"]}`; `"*"` covers every module (so a module added tomorrow isn't silently forbidden) and `null` means unrestricted (`super_admin`). Enforcement is the **`permission:` middleware** (`EnsureModulePermission`) on the `module:*` route groups — the action is derived from the HTTP method, with `resync`/`watched`/`bulk-status`/`reorder` treated as `update`. ⚠️ `$user->role` is now a **relation object**: use `roleKey()` for string comparisons and `assignRole('key')` to set it (`User::creating` backfills the `user` role). Policies still check ownership only. Frontend: `useAuth().can(module, action)` for hiding buttons; `/roles` + `/roles/:id` (matrix) manage them. **The admin sections are role-grantable too (Tasks 1.6, 2026-09-06)**: `roles.permissions` also accepts the reserved keys **`admin:users` / `admin:roles` / `admin:requests` / `admin:audit`**, enforced by the **`admin_access:<resource>`** middleware. ⚠️ **`"*"` deliberately does NOT grant them** — it means "every module", and letting it reach the admin zone would silently hand the user-management panel to any power-user role (pinned by `OwnershipTest`). ⚠️ **`admin/modules` and `admin/purge` stay `super_admin`-only** on purpose: disabling a module affects *every* account and purge deletes someone else's library, so neither belongs to a single section's permission. Frontend: `useAuth().canAdmin(resource[, action])` drives the links, the routes and the in-page guards — don't check `is_super_admin` directly for these three.

**Auth & multi-tenancy (I7)** — Sanctum **SPA cookie** mode (`$middleware->statefulApi()`, `SANCTUM_STATEFUL_DOMAINS`, `cors.supports_credentials=true`; axios uses `withCredentials`+`withXSRFToken` and hits `/sanctum/csrf-cookie` before login). Every `/api` route sits behind `auth:sanctum` except `/health` and `/auth/{register,login}`. Ownership is **per-user rows**: `movies.user_id`/`series.user_id` + the `BelongsToUser` trait (global scope `owner` + auto-fill on create), so every existing query, `withCount`, and route-model binding scopes itself — another user's record is a **404**. Policies (`MoviePolicy`/`SeriesPolicy`) are the second layer; `Gate::before` lets a super-admin pass any policy but the `owner` scope still applies to them (admin data access is only via `/api/admin/*`, which uses `withoutGlobalScope('owner')` explicitly). **`genres`/`cast_members` stay global** (shared dictionaries). ⚠️ CLI has no `Auth::id()`, so the scope is off there — `media:redownload --user=` exists for that.

**Modules (I2/I3)** — `modules` table (`key`, names ka/en, `icon`, `route_base`, `api_base`, `morph_alias`, `enabled_by_default`, `is_active`) + `module_user` pivot. `movie`/`series` are the first two entries (`ModulesSeeder`). Routes are grouped behind `module:movie` / `module:series` / `module:@type` (the last reads the `type` param for shared endpoints). Frontend nav and routes are built from `GET /api/modules` (`lib/modules.tsx` → `ModulesProvider`/`useModules`), so a disabled module has **no menu entry and no route**; `lib/media.ts` still supplies the static descriptor for domains that use the generic pages. ⚠️ The written recipe for adding a module **no longer exists** (its doc was deleted 2026-09-07); the registry checklist in `Tasks.md` §7.1 is what replaced it.

**Videos module (I5)** — the first non-media module and the proof of the recipe: `videos` table (`BelongsToUser`), `VideoController`, `VideoPolicy`, routes behind `module:video`. **Types are a per-user dictionary** (`video_types` + `videos.type_id`, `VideoType`/`VideoTypeController`/`VideoTypePolicy`, page `/video-types`) — the old `videos.kind` enum is gone; `VideoType::ensureDefaults()` lazily creates „ინფორმაციული"/„გასართობი" on first read, and the sidebar sections are built from that list with **„რჩეული" pinned last**. `videos.visibility` (`private` default) already exists for `Tasks.md` §16, but no UI exposes it yet (`movies`/`series` now have the same column). `App\Support\VideoUrl` recognises YouTube / Vimeo / Dailymotion / direct file and builds the embed itself — **raw HTML/embed markup is never stored**; `VideoEmbed.tsx` re-checks the host against the same allowlist and sandboxes the iframe. Uploaded thumbnails, files (`video_files` — photos and documents) and notes (`video_notes`) all go to the **public** disk. `video_files`/`video_notes` cascade in SQL, but `Video::booted()` still deletes files one by one — a DB cascade fires no model event, so the file on disk and the quota counter would be left behind. Frontend registration for a non-media module is two lines: `PAGE_MODULE_KEYS` (`lib/modules.tsx`) + `MODULE_PAGES` (`App.tsx`).

**Local video download (Tasks §7.1, built 2026-09-12)** — `yt-dlp` pulls a video into the library: `Services/Video/YtDlp` (the only place the binary is invoked), `Services/Video/VideoDownloader` (quota + columns), `Console/Commands/DownloadVideoCommand`, `Api/VideoDownloadController` and `Support/BackgroundProcess`. Endpoints: **`POST|GET|DELETE /api/videos/{video}/download`** (start · serve · free) plus `GET /api/videos/download-status`. The four decisions came from the user on 2026-09-12: **`yt-dlp` + optional `ffmpeg`**, **best available quality**, **counts against the quota**, **private disk**. Ten things are easy to get wrong:
- ⚠️ **The file is columns on `videos`, not a `video_files` row** (`download_path`/`download_name`/`download_size`/`download_format`/`download_status`/`download_error`/`downloaded_at`). A video has at most one local copy, so the question is "does it have one", not "how many"; and a 1 GB file in `video_files` would render inside the attachments grid as a "document".
- ⚠️ **`download_status` distinguishes four facts and a boolean cannot**: `null` (never tried) · `running` · `failed` + `download_error` · `ready`. The UI shows a different button for each; collapsing them made "why is nothing happening" unanswerable.
- ⚠️ **The download runs detached, not in the request.** `artisan serve` is single-threaded, so a synchronous multi-minute download would freeze the whole dev server — the same reason sync/gallery/purge are queues. `Symfony\Process` is unusable here (it kills the child in `__destruct`), so `BackgroundProcess` shells out (`start /B` on Windows) to `php artisan videos:download {id}`. The SPA polls the list every 4 s **only while something is `running`**.
- ⚠️ **`videos/downloads` is private while `videos/thumbnails` stays public** — the first case of a private sub-folder inside a public root. `StorageFolder::PRIVATE_ROOTS` matches the *first* segment on purpose (so a future `notes-archive/` can't go private silently), so a second list, **`PRIVATE_FOLDERS`**, matches two segments — still segment-wise, so `videos/downloads-old` is not caught.
- ⚠️ **Such a folder must also be listed in `StorageMeter::UPLOAD_FOLDERS` separately**: the orphan scan picks one disk per folder, so scanning the public `videos` root would never see the private sub-folder and its orphans would live forever.
- ⚠️ **`referencedPaths()` is now a flat `table.column` list, not a `table => column` map** — `videos` owns *two* path columns and the map silently kept only one, which would have made the admin's orphan cleanup delete every downloaded video. `RegistryConsistencyTest`'s source-parsing regex was updated with it (its three anchors are what stop that read from passing vacuously).
- ⚠️ **The quota is checked twice and both are needed**: before (yt-dlp's `filesize_approx`, so a 30-minute download doesn't start doomed) and after (the real size). Over quota after the fact **deletes the file** — a limit that can be exceeded is not a limit.
- ⚠️ **`storeLocalFile()` streams**; `storeContents()` would have read a gigabyte into a PHP string.
- ⚠️ **Missing binaries are a state, not a crash**: `YtDlp::available()` false → **503 `ytdlp_unavailable`** (registered in `lib/errors.ts`), and a second start while one runs is **409 `download_already_running`** (two parallel runs would spend the quota twice). `ffmpeg` is optional but *decides quality*: without it `bv*+ba` cannot merge, so the selector falls back to `b` and the UI says so — what actually arrived is stored in `download_format` and shown.
- ⚠️ **`download` had to join `EnsureModulePermission::UPDATE_ENDPOINTS`** or a view+update user would get a spurious 403 from the POST. The file leaves the server through the ownership-checked `GET` only (404, never 403), `Video::deleteDownload()` releases the **recorded** `download_size` (the `StoredFile` rule) and is called from `Video::booted()` so `PurgeService` frees it too.

**Bookmarks module (Tasks §18)** — `bookmark`, built 2026-09-07 after the user picked it (and deferred anime) in `DECISIONS.md` §10. It is the **second module with no external source at all** (the first is `note`), so there is no candidates→draft flow: one probe, `POST /bookmarks/metadata`, reads the page's own `<head>`. Two tables: `bookmarks` (`BelongsToUser`, `HasCustomFields`, `visibility`) and `bookmark_categories` (**per-user dictionary**, `/bookmark-categories`, `ensureDefaults()` seeds 6 lazily). Routes: `GET|POST /bookmarks`, `POST /bookmarks/metadata`, `GET|PUT|PATCH|DELETE /bookmarks/{bookmark}`, `PATCH /bookmarks/{bookmark}/{favorite,status}`, `POST /bookmarks/{bookmark}/visited`, plus the dictionary (`GET|POST /bookmark-categories`, `PUT|PATCH|DELETE /bookmark-categories/{bookmarkCategory}`, `POST /bookmark-categories/reorder`). Five things are easy to get wrong:
- ⚠️ **The category is a single column (`category_id`), not a pivot** — deliberately unlike `song`/`game`. A category here is a *folder* (a link lives in one place) and `tags` covers every other axis; that is `note`'s exact precedent. Consequence: the list filter is `whereIn` (so a comma-separated list is **OR**, not AND) while tags stay AND.
- ⚠️ **`domain` is a column, not an accessor.** Grouping and filtering happen on it, which SQL cannot do without a column. `Bookmark::applyUrl()` is the **only** place it is written (it lowercases and strips `www.`, so `example.com` and `www.example.com` are one group).
- ⚠️ **og:image is never downloaded** — it stays as a remote URL in `image_url`. Downloading it would spend quota on something already public. The only metered upload is `thumbnail_path` (`bookmarks/thumbnails`), exactly like a song's.
- ⚠️ **There is no unique index on `url`.** The column is 1000 chars; utf8mb4 makes that 4000 bytes, over MySQL's 3072-byte index limit, and a hash column is more ceremony than a duplicate bookmark is worth.
- ⚠️ **`POST .../visited` needs `visited` in `EnsureModulePermission::UPDATE_ENDPOINTS`** — otherwise the middleware derives `create` from POST and a view+update user gets a spurious 403.
`Services\Bookmarks\LinkMetadata` parses `<title>`, Open Graph/Twitter cards and the favicon out of the first 200 kB of the response; **raw HTML is never stored** (the `VideoUrl` rule) and a failure is a **200 with empty fields**, not a 5xx — a page that 403s a bot is ordinary, and it must not block manual entry.

**Songs module + playlists (Tasks §15)** — ⚠️ **the earlier "a song is a `videos` row" decision was reversed by the user on 2026-09-03.** A song now has its own module (`song`), because a sidebar section, an admin toggle and per-module CRUD rights in the role matrix all hang off a `modules` row — none of that is reachable from a sub-section. Schema: `songs` (`BelongsToUser`, `HasGallery`, `visibility`) with the **full music field set** — `title`, `artist`, `album`, `year`, `genre_id`, `duration`, `tags`, `rating` (1–10), `url`/`platform`/`embed_url`, `thumbnail_path`, `is_favorite`, `play_count`/`played_at` — plus `song_genres`, a **per-user dictionary** (`SongGenre`, page `/song-genres`, `ensureDefaults()` seeds 8 genres lazily). ⚠️ The global `genres` table is deliberately *not* reused: it holds TMDB movie genres, and "Rock" would show up in the movie genre picker. A song carries **one** `genre_id` (tags cover the rest) — a pivot can be added later if that proves too thin. ⚠️ **A song is multi-genre since 2026-09-07** (`DECISIONS.md` §5, answered against my recommendation): pivot `song_genre_song`, and `songs.genre_id` is **gone**. The consequences mirror `game`'s — the list filter is `whereHas` (AND across a comma-separated list), deleting a genre with `move_to` **adds** the songs to the target (`syncWithoutDetaching`) so the song's other genres survive, and `PurgeService`'s `type` mode reads the pivot. ⚠️ That special case is now a **map** (`PurgeService::GENRE_PIVOTS`), not an `if`: there are two multi-genre domains, and a third would otherwise add a third branch. ⚠️ The column drop is **MySQL-only** — sqlite cannot `DROP COLUMN` while a foreign key names it, so on the test database the dead column survives and nothing reads it. The URL goes through the same `VideoUrl` allowlist and the same `VideoMetadata` probe as videos, so no HTML is ever stored. **Playlists live in the song module** (`playlists` + `playlist_song`, routes inside `module:song`, pages `/playlists` and `/playlists/:id`). Ordering exists at **two levels**: `playlists.sort_order` (`POST /playlists/reorder`) and `playlist_song.sort_order` — the latter set by `PUT /playlists/{playlist}/songs`, which takes the **whole ordered list**, so add / remove / drag-reorder are one operation and `sort_order` can never desync. The reverse direction (`PUT /songs/{song}/playlists`) backs the playlist multi-select on the song form. ⚠️ **Both pivot endpoints are `PUT`, not `POST`, on purpose** — `EnsureModulePermission` derives `create` from POST, so a user with update-but-not-create rights would get a spurious 403. `songs.visibility`/`playlists.visibility` exist (`private` default, §16) but **have no UI toggle yet** — public only shows as a badge. **A song carries its own files and notes since 2026-09-11 (Tasks §7.4)**: `song_files` (`kind` = `image|doc`) + `song_notes`, the 2026-09-03 section-table rule, exactly `video_files`/`video_notes`' shape — rendered by `components/SongDetail.tsx` (photos · notes · documents) behind a paperclip button in the list. ⚠️ **There is no `audio` kind on purpose**: a song's own recording is `songs.url`, and an uploaded track would add tens of megabytes per record to the quota; the task asked for "like `video_files`". ⚠️ `Song::booted()` deletes the files one at a time despite the SQL cascade — a cascade fires no model event, so the file on disk and the quota counter would be left behind (pinned by a test that deletes **through the model**, which is the path `PurgeService` takes). Drag & drop is `lib/dragReorder.ts`: native HTML5 DnD, **no library added** (dnd-kit would cost ~40 kB on an already 1 MB bundle); it also returns `moveBy()` because native DnD is not keyboard-accessible, which is why the up/down buttons stay.

**Playback (Tasks §7.2, built 2026-09-11)** — one player for the whole app: `lib/player.tsx` (`PlayerProvider`/`usePlayer`, the queue), `components/PlayerBar.tsx` (the bottom strip) and `components/PlayerStage.tsx` (the only place media actually plays). **Frontend only — no backend change**: `embed_url` and `POST /songs/{song}/played` / `POST /videos/{video}/watched` already existed. Where it starts: a song's cover on `/songs` (queue = the **filtered list**), `/playlists` (a row's ▶ fetches the playlist first, since the list payload carries only `songs_count`), `/playlists/:id` (header "play all" + each row) and `/videos` (header "play all" + a per-card ▶; **the thumbnail still opens `VideoDetail`** — one video is better watched in the wide modal than in a 256 px strip). Eight things are easy to get wrong:
- ⚠️ **The provider sits in `App.tsx` above `<AppShell>`, and `<PlayerBar />` outside `<Routes>`.** That is the whole feature: a player that unmounts on navigation cannot finish a playlist. The old `components/SongPlayer.tsx` modal was deleted for exactly this reason — it could not survive a route change, and two embeds sounding at once is worse than one.
- ⚠️ **The allowlist is `lib/embed.ts` now, not `VideoEmbed.tsx`.** `isAllowedEmbed`/`ALLOWED_EMBED_HOSTS` mirror `VideoUrl::EMBED_HOSTS`; `playableEmbedSrc()` only *adds query params* (`autoplay`, and for YouTube `enablejsapi`+`origin`) to the URL the backend built. **Raw HTML is still never stored or rendered** — the project's hard rule.
- ⚠️ **`enablejsapi`+`origin` are load-bearing, not decoration.** Without them a YouTube frame neither sends nor accepts `postMessage`, so "it ended" is unknowable and auto-advance — the point of the task — silently does nothing.
- ⚠️ **Every platform names the same event differently**, so `embedEventFrom()` is one decoder: YouTube's `{event:'infoDelivery', info:{playerState}}` (0/1/2), Vimeo's `{event:'ended'|'play'|'pause'}` and Dailymotion's `event=video_end` query-string form all collapse to `ready|playing|paused|ended`. A second copy of this mapping would drift the day a player changes.
- ⚠️ **The `message` listener checks `e.origin`.** Any frame on the page can post to us, and an unchecked message would skip a track.
- ⚠️ **The frame is recreated per track (`key`), not reused with `loadVideoById`.** Reuse is smoother but racy: a command sent before the player is ready is dropped and the track never starts. A fresh frame with `autoplay=1` is correct by construction — the browser's sticky activation (the user already clicked play) permits it.
- ⚠️ **`ended` is guarded by the activation counter (`seq`)**, because YouTube can send it twice and the queue would jump two tracks.
- ⚠️ **"Played" is counted on activation, not on finish** — the same moment the old button counted it, now including auto-advanced tracks. A failed counter is swallowed: it must not interrupt playback.
- ⚠️ **`--player-h` is the only channel between the bar and the rest of the page** — `<main>` reads it as bottom padding and the queue toast adds it to its own `bottom`. The variable exists only while something is playing. The bar's z-index lives in `lib/layers.ts` (`LAYER_PLAYER`, 50: above the header, below modals).
- ⚠️ **`platform === 'other'` says so out loud** ("this source cannot play in the app — open the original") instead of rendering a black box; auto-advance genuinely cannot work there. The i18n namespace is **`playback.*`, not `player.*`** — `player.vimeo.com` in the allowlist would otherwise trip the i18n audit's "key-like literal outside `t()`" check.

- `Services/Video/VideoSearch` — `search()` covers **everything** (title, description, tags, notes, source/platform, URL) with an mb-aware Levenshtein for near-miss terms and hand-rolled relevance; `similar()` powers `GET /videos/{video}/similar` from the user's own library (shared tags + title similarity + same platform/type). **FULLTEXT is deliberately unused** — sqlite tests have none and it handles Georgian poorly.
- `Services/Video/VideoMetadata` — backs `POST /videos/metadata`; `hasYoutubeKey()` reports whether a YouTube API key is configured so the UI can degrade gracefully.
- `lib/videoDuration.ts` (frontend) — `isDirectMediaUrl()` + `probeMediaDuration()` read `.mp4`/`.webm` length from a hidden `<video>` element in the browser, so the server never downloads the file. `formatDuration()` renders it.

**Tables are named per section (user decision, 2026-09-03)** — there is **no universal `attachments`/`notes` table any more**. Each section owns its own: `gallery_images` (still polymorphic — one photo mechanism for movie / series / cast_member / song), `video_files` (`video_id` FK, `kind` = `image|doc`) and `video_notes` (`video_id` FK). The trade-off was accepted explicitly: a future module that needs files brings its **own** `<module>_files` / `<module>_notes` migration, in exchange for a table name that says what is inside it. Shared behaviour lives in two small pieces, not in a shared table: `Concerns\StoredFile` (delete the file from disk + release the quota on `deleted`) and `Concerns\HasGallery` (the `galleryImages()` morphMany, the `galleryVideos()` morphMany added in §8.1, and **`deleteGalleryMedia()`** — renamed from `deleteGalleryImages()` because after videos the old name lied, and a lying cleanup name is exactly how orphan rows and leaked quota happen).

**Books module (Tasks §12)** — `book`, built 2026-09-04 on the same recipe as `song`. Four tables: `books` (`BelongsToUser`, `HasGallery`, `visibility`), `book_genres` (**per-user dictionary**, `/book-genres`, `ensureDefaults()` seeds 10 genres lazily), `book_files` (`kind` = `book|image|doc` — the ebook itself is `book`, max 50 MB) and `book_notes` (`is_quote` + `page`, so a quote is the same row with two extra fields, not another table). ⚠️ **Bilingual text is flat columns** (`title_ka`/`title_en`, `description_*`) with **no translation table**: those exist for movies because TMDB serves two languages and §7's translator is built on them, whereas Open Library is monolingual — the API shape stays identical to `MovieResource` either way. ⚠️ **Reading progress is stored in two units** (`progress_page` + `progress_percent`) and `Book::syncProgress()` writes both at once — page wins when `pages` is known, percent is the only unit for audiobooks; the same rule TMDB posters follow. Only `cover_source = 'upload'` is metered and deleted. `Book::booted()` deletes `book_files` one by one for the usual reason (a SQL cascade fires no model event, so the disk and the quota counter would drift).

**Board games module (Tasks §14)** — `board_game`, built 2026-09-04 on the books recipe. Four tables: `board_games` (`BelongsToUser`, `visibility`), `board_game_genres` (**per-user dictionary**, `/board-game-genres`), `board_game_files` (`kind` = `rules|image|doc`) and `board_game_notes`. ⚠️ **The gallery lives in `board_game_files` (`kind = 'image'`), not `gallery_images`** — that is the existing rule, not an exception: `gallery_images` holds photos *downloaded from TMDB*, while a user's own *uploads* live in the section table (exactly like `video_files.kind = 'image'`). ⚠️ **The title is single-language** (`title`), unlike a book's — §14 doesn't ask for two and BGG is English-only. ⚠️ **Mechanics are a JSON array, not a second dictionary**: the genre is one (`genre_id`), mechanics are up to ten per record and come straight from BGG. ⚠️ **Price hangs off the shop link** (`links[].price`/`currency`), not off the record — one `price` column could not describe two shops. Enrichment is `Services/BoardGames/BggClient` (XML API 2 — the only XML source in the project; `SimpleXML`, all parsing inside try/catch). ⚠️ **BGG is unreachable from this machine (verified 2026-09-04)**: `boardgamegeek.com` answers with a Cloudflare bot challenge (403) and the API with 401, so `BggClient::blocked()` separates "source down" from "no results" and the endpoints return **503 `bgg_unavailable`** — otherwise an empty list would read as "this game doesn't exist". A downloaded image is `image_source = 'bgg'`, named after `bgg_id`, doesn't count against the quota and is **never deleted with the record** (the shared-file rule TMDB posters and book covers follow). **Georgian shops are live since 2026-09-11 (Tasks §7.2)**: `Services/BoardGames/GeorgianShops` scrapes **corners.ge** (WooCommerce) and **puzz.ge** (OpenCart) — the two sources the user named, and both *do* answer from this machine, unlike BGG. `GET /api/board-games/shops?query=&shops=` returns `offers[]` (title · url · image · price · old_price · currency · in_stock · shop) + `sources[]`. Six things are easy to get wrong:
- ⚠️ **It is a `GET`, not a `POST`.** `EnsureModulePermission` derives `create` from POST, so searching the shops while *editing* an existing game (update rights, no create) would have been a spurious 403 — the same trap `PUT /playlists/{playlist}/songs` avoids.
- ⚠️ **Three different silent failures, and they must stay distinguishable.** Page didn't open → `sources[].ok = false` ("the shop isn't answering"); opened and found nothing → `ok: true, count: 0`; found the item but not the price → `price: null` ("price unknown"). None of them is a 5xx — a shop's broken markup must never block adding a record (the `LinkMetadata` / `bgg_unavailable` rule).
- ⚠️ **The real markup differs from what §7.2 described** (verified 2026-09-11, fixtures committed). On corners.ge the listing uses `span.price`, not `p.price` (that one is the single-product page) — so the selector is on the **class**, not the tag; discounts are `<del>`/`<ins>` as documented. On puzz.ge the listing is `div.price` → `span.price-normal`, discounted `span.price-new` + `span.price-old`; the `.product-price-*` names in the task are the product page's. **Both sets are accepted** so one disappearing doesn't take the other with it.
- ⚠️ **puzz.ge lazy-loads images** — `src` is a base64 placeholder and the real URL is in `data-src`, so reading `src` would give every row the same grey square.
- ⚠️ **The price belongs to the shop link, not to the record** — it goes into the existing `links[].price`/`currency`, and no column was added: two shops can't fit in one column.
- ⚠️ Parsing is `DOMDocument`/`DOMXPath` (**no library added**), with `libxml_use_internal_errors` around it (`BggClient`'s trick), and a successful response is cached 15 minutes — **a failure is never cached**, or one flaky second would read as "unavailable" for a quarter hour. The tests run on the shops' **real markup** (`backend/tests/Fixtures/{corners,puzz}-search.html`), which is what makes them worth having.

**Games module (Tasks §11)** — `game`, built 2026-09-04 after the user approved §11.1's field list as-is (§19.1). Six tables: `games` (`BelongsToUser`, `HasGallery`, `visibility`), `game_genres` (**per-user dictionary**, `/game-genres`, `ensureDefaults()` seeds 13 RAWG-style genres lazily), **`game_genre_game`** (the pivot), `game_videos` (§11.2), `game_files` (`kind` = `image|doc`) and `game_notes`. Four things differ from every other module and are easy to get wrong:
- ⚠️ **The genre is a per-user dictionary even though §11.1 says "shared polymorphic `genres`, like movies".** §11.1 was written 2026-09-02, one day *before* the per-user rule was set for songs; RAWG's genres are `Shooter`/`RPG`/`Platformer`/`Massively Multiplayer`, which in the global table would show up in the **movie** genre picker.
- ⚠️ **But it stays multi-genre** (pivot `game_genre_game`), unlike book/board game's single `genre_id` — §11.1 says "genres", plural, and a game really is Action + RPG + Adventure at once. Consequences: the list filter uses `whereHas` (not `whereIn` on a column), `PurgeService`'s `type` mode special-cases `game`, and deleting a genre with `move_to` **adds** the games to the target (`syncWithoutDetaching`) instead of overwriting a column — the game's other genres must survive. There are no tags; genres and platforms cover that axis.
- ⚠️ **There is no `year` column** — `Game::year` is an accessor over `release_date`. Two units for one fact drift apart (the trap `Book::syncProgress()` fights), so sorting by "year" orders by `release_date` in SQL. **`franchise` has no dictionary table either, for the same reason** (Tasks §5.1): it is the game's own text column and RAWG returns it that way, so the picker list is aggregated straight out of it by **`GET /api/games/franchises`** (name + count, `owner`-scoped) and `components/GameFranchiseDialog.tsx` renders name · parts already in the library · **"add a new part"** (a RAWG search that creates the record immediately, independently of the parent form). ⚠️ The list filter `?franchise=` is an **exact** match, not `like` — otherwise "Mass Effect" would swallow "Mass Effect: Andromeda".
- ⚠️ **Videos live in `game_videos`, not in the `videos` table.** That table is the video *module's* library (own type dictionary, search, stats); a game's walkthrough is part of the record and must not appear in the videos list. The URL still goes through the `VideoUrl` allowlist and `GameVideo::applyUrl()` is the single place that (re)derives `platform`/`embed_url` — raw HTML is never stored. `kind` defaults to `walkthrough`, which §11.2 calls the mandatory one.

Screenshots live in **two** places and that is the existing rule, not an exception: RAWG-**downloaded** shots go to `gallery_images` (morph alias `game`, §11.3 → §10's mechanism), the user's **uploads** to `game_files.kind = 'image'` — exactly like video and board game. Enrichment is `Services/Games/RawgClient` (chosen over IGDB in §11.4 because it needs one free key, not a Twitch OAuth loop); `RAWG_API_KEY` is **optional** — without it the endpoints return **503 `rawg_unavailable`** and the form says "source unavailable" rather than "nothing found", the same distinction `BggClient` makes. **`Services/Games/IgdbClient` was added 2026-09-07 as a *fallback*** (`DECISIONS.md` §7, answered against my recommendation): `candidates()` tries RAWG first and only falls through to IGDB when RAWG brings nothing back, and `lookup` accepts `rawg_id` **or** `igdb_id`. Four things are easy to get wrong:
- ⚠️ **503 means *both* sources failed** (`GameController::blocked()`). One working source returning nothing means the game really wasn't found, and calling that "source unavailable" would be a lie.
- ⚠️ **A candidate row carries `source`**, and an IGDB row has `rawg_id: null` — sending that to `lookup` would 422, so `fetchRawgDraft()` picks the body from `candidate.source`.
- ⚠️ **`cover_source` stays `'rawg'` even for an IGDB cover.** That column answers "uploaded or fetched", and it is what `Game::deleteCover()` and the quota rule key on; a third value would need a branch in both places, and the first one forgotten would either delete a shared file or leak quota forever.
- ⚠️ **Matching (§16.2) still keys on `rawg_id` only** — `PublicDomain::MATCH` takes one identity per domain, so an IGDB-only game simply doesn't take part, which is the documented "null identity column" rule. `IGDB_CLIENT_ID`/`IGDB_CLIENT_SECRET` are both optional; the Twitch token is cached (`Cache` key `igdb.access_token`) and dropped on a 401 so the next call re-fetches. The query language is **APIcalypse** (a SQL-ish body on a POST), which is why this is its own client and not a flag on `RawgClient`. A downloaded cover is `cover_source = 'rawg'`, named after `rawg_id`, doesn't count against the quota and is **never deleted with the record**. **HowLongToBeat times are entered by hand** — no official API (§11.4). ⚠️ **`hltb_*` are minutes, not hours, since 2026-09-11 (§2.5)**: the columns were `decimal(5,1)` hours, so „2h 20m“ was stored as 2.3 and read back as 2h 18m. They are `unsigned int` minutes now — the same unit `movies.runtime` uses — and the form is the shared `DurationInput`. The migration converts the values **in PHP, not with `UPDATE … * 60`**: the old column capped at 9999.9, so 200 hours in minutes would have been silently truncated by a write into the same column.

**Notes module (Tasks §13)** — `note`, built 2026-09-04. It is the only module whose content is **purely the user's own** — no external source, so no lookup/enrichment at all. Five tables: `note_entries` (`BelongsToUser`, `visibility`), `note_categories` (**per-user dictionary**, `/note-categories`, `ensureDefaults()` seeds 6 lazily), `note_entry_files` (`kind` = `image|video|doc`; video capped at 100 MB), `note_reminders` (§13.2) and `note_notifications` (the delivery queue + log, §13.3). Five things are easy to get wrong:
- ⚠️ **The table is `note_entries`, not `notes`.** Under the 2026-09-03 rule the universal `notes` table is gone and the name now means "a note attached to some other record" (`video_notes`, `book_notes`…). A note here is a standalone entity. The module key and the API base are still `note`/`/notes`.
- ⚠️ **§13.1 asked for `HasAttachments`, which no longer exists.** Its replacement is the section's own `note_entry_files` + `Concerns\StoredFile`, so quota accounting and disk deletion come for free — same shape as `video_files`.
- ⚠️ **A reminder carries its own `timezone`.** The app runs on UTC (`config/app.php`), the user does not: "every day at 09:00" without a zone fires at 13:00 in Tbilisi. `mode = once` stores an absolute UTC instant and needs no zone; every recurring mode stores wall-clock `time_of_day` + `timezone` (the browser's `Intl` zone). **`NoteReminder::computeNextAt()` is the only place `next_at` is derived** — a second formula would double-fire.
- ⚠️ **There are six modes since 2026-09-11 (Tasks §5.5)**: `once` · `interval` · `daily` · `weekly` · **`monthly`** (`day_of_month`) · **`yearly`** (`month` + `day_of_month`), plus **`repeat_count`** (total firings; `null`/`0` = forever). Three traps: **`weekday` was replaced by `weekdays` (a JSON array)** — keeping both would store one fact twice, so the migration backfills the array and drops the column **on MySQL only** (sqlite can't, and nothing reads the dead column — the `songs.genre_id` precedent); **day 31 clamps to the month's length** in `NoteReminder::atDay()`, because Carbon's default overflow turns `Feb 31` into `Mar 3` and would silently pick the wrong month; and **`repeat_count` is decided in exactly one place** (`exhaustedAfter()`), for the same reason `next_at` has one formula. `weekly` picks the **nearest** of the selected days.
- ⚠️ **`GET /note-reminders/due` is a GET that also fires due reminders.** Deliberate: no cron runs on the dev machine and §13.3 promises the browser channel works "with no dependency", so the SPA's poll drives the same `ReminderDispatcher` the cron does. It cannot be a POST — `EnsureModulePermission` derives `create` from POST, so a view-only user would never receive a reminder.
- ⚠️ **A reminder can never fire twice.** The dispatcher claims each row with a conditional UPDATE (`where next_at = <the value we read>`) *before* sending; a second caller (cron vs. an open tab) gets 0 rows and skips. Sending happens after the claim because Telegram/SMTP can take seconds.

Delivery channels (§13.3): `browser` is a queue row the SPA polls (`lib/noteReminders.ts` → `useNoteReminderWatcher`, mounted in `AppShell` so it works on any page) and shows via `public/sw.js`'s `showNotification()`, falling back to `new Notification()`; `telegram` is one HTTPS call (`Services/Notes/TelegramNotifier`, **no key in `.env`** — the user's own bot token lives in `module_user.settings`). ⚠️ **The email channel was removed on 2026-09-11 (§8.2)** — `NoteReminder::CHANNELS` is `['browser', 'telegram']`, `sendEmail()` and the `Mail` import are gone, and asking for `email` is now a **422 rather than a silent skip**: there is no SMTP here, so a silently accepted channel told the user a letter was on its way. Its replacement is a **log**, not a queue: `GET /api/note-notifications` + `components/NoteNotificationsDialog.tsx` (the bell on `/notes`) keeps every fired reminder **including the read ones**, while `GET /note-reminders/due` still returns only what should pop up and clears on read — a log that empties itself is not a log. A failed send shows `failed` + the reason („no Telegram bot configured“ and „the reminder never arrived“ are different facts). The migration drops `email` from existing rows and puts `browser` in its place when it was the **only** channel, or the reminder would stay „active“ and reach nobody; old `note_notifications` rows stay (they are history, labelled „email (no longer used)“). This is also what removed the `schedule:work` dependency: browser polling delivers while the app is open and nothing is lost while it is closed — it is in the log. Per-user channel config is `module_user.settings` via `NoteChannelSettings`, edited from the gear button on `/notes` (`NoteChannelsDialog`) — not `users.settings`, which is account-wide. A failed send is recorded in `note_notifications.error` and never stops the loop.

**Gallery module (Tasks §10 → §8 „gallery 2.0", rebuilt 2026-09-12)** — `gallery` is a module with **six pages of its own**. Content is rows in **`gallery_images`** (`source`, `category` = `backdrop|poster|logo|actor`, `remote_path`, `width`/`height`) and, since §8.1, **`gallery_videos`** (a *link*, not a file — see below). Both hang off the same parents, and the list of parents is one map, **`App\Support\GalleryParent`**: `cast_member` · `movie` · `series` · `anime` · `song` · `book` · `game`. ⚠️ **That map exists because the same list used to be written three times** (`WebSearchController::TARGETS`, the groups loop, `withOwners()`) and two of the copies only knew `MediaDomain::TYPES` — so a photo imported onto a song landed in the database and then **appeared nowhere in the gallery**. Every parent uses `HasGallery` and calls **`deleteGalleryMedia()`** in `booted()` (renamed from `deleteGalleryImages()` — after videos the old name lied, and a lying name is how orphan rows happen). `gallery_images` stays **polymorphic on purpose** — it is the one shared table the section-per-table rule keeps, because quota accounting (§17) and the delete cascade then come for free; no `visibility` column is needed either, since a photo inherits its parent's visibility (§16). ⚠️ In the storage breakdown a gallery photo is attributed to the **`gallery`** module, not to `imageable_type` (which is `cast_member` for actor photos — not a module key).

**Where it shows up:** `/gallery` is a real section with a **sidebar sub-menu**, and the list of cuts is one constant, `GALLERY_CUTS` in `pages/GalleryPage.tsx` (the sidebar imports it — two copies would drift): **ყველა ფოტო** `/gallery` · **ჩანაწერები** `/gallery/records` · **მსახიობები** `/gallery/actors` · **ვიდეოები** `/gallery/videos` · **წყაროები** `/gallery/sources` · **მოდულები** `/gallery/modules`. Drilling into a record opens `/gallery/records/:type/:id` (`pages/GalleryRecordPage.tsx`), and `/gallery/actors/:id` **redirects to `/actors/:id`** — an actor has exactly one page. The record page keeps its inline gallery below the trailer (`components/RecordGallery.tsx`), and the same component backs the gallery's record page with `bare` — one body, two mount points.

⚠️ **The line-divided „მასობრივი ჩამოტვირთვა" block is gone** (the user's direct instruction). It sat two different jobs — browsing and downloading — on one scroll and stripped the download of its context, making you re-pick a scope that was already known. Downloading is now either the page-header button (with a scope picker) or a button **on the group card / record / actor**, and it is always the same dialog, `components/GalleryDownloadDialog.tsx`. `GET /api/gallery` is therefore no longer „the list of records to download from" but the **summary** that feeds the sub-menu counters (photos · records · actors · videos · bytes · storage) — three separate `groups` calls would have downloaded three full lists just to draw a menu.

**Downloading** is `Services/Gallery/GalleryFetcher`. ⚠️ **Counts and sizes are per subject now** (§8.2): `subjects` ⊂ `stills|posters|logos` with `limits`/`sizes` maps. The old single `limit` concatenated the candidates (stills first) and sliced afterwards, so on a record with 40 backdrops and `limit = 20` **no poster ever arrived**. ⚠️ **The size list comes from the subject** (`GalleryFetcher::SUBJECT_SIZES`, TMDB `configuration`, verified live 2026-09-12): backdrop `w300·w780·w1280·original`, poster `w185·w342·w500·w780·original`, logo `w154·w300·w500·original`, profile `w45·w185·h632·original`. The CDN does accept a foreign key (a poster at `w1280` returns 200) but a **nonexistent** one is a 400, so the offered list must be the subject's. ⚠️ **An actor has two sources** (`cast_source` = `profiles|tagged|both`): `/person/{id}/images` (portraits — often only 3–5) and **`/person/{id}/tagged_images`** (stills and posters of the films the person is tagged in — tens; Joaquin Phoenix: 17 vs 47, measured). `both` takes portraits first because a portrait is the actor's photo while a still is the film's. Tagged rows keep **TMDB's own `image_type`** as `category` (`still` → `backdrop`) so the actor page can tell a portrait from a film still, and `original_name` carries the film's title so „which film is this from" has an answer. `tagged_images` is paginated (20/page, capped at `MAX_TAGGED_PAGES` = 10 = `MAX_PER_ACTOR`). Cast selection is `all|female|male|selected`; gender comes from TMDB (`cast_members.gender`, 1=female/2=male) and is **backfilled from one `credits` call** when null, only when the scope is at most `GENDER_BACKFILL_RECORDS` (10) records — one request per record would turn a library-wide plan into minutes; otherwise the plan returns `unknown_gender` and the UI names the number.

**Scope** is `Services/Gallery/GalleryScope` — one builder for both targets, because the actor pool *is* the scope's cast. ⚠️ It is **multi-domain** now (`types[]`: „films, series and anime together" is one run, not three), statuses are a **list**, genres carry a **`genre_mode` = `any|all`** (three genres ANDed usually produced an empty scope that read as „I have nothing"), `ids` accepts the per-domain map `/sync` already uses, and **`scope = off`** exists on the actor target only — „turn the scope off and download on actors generally". ⚠️ Under `scope = ids` a domain with no selected ids contributes **nothing**, not everything (`/sync`'s old permissive reading would have downloaded the whole library). ⚠️ **`cast = selected` is read outside the pool cap**: the pool is the first `CAST_POOL_LIMIT` (1000) members by name and is narrowed further by `cast_q`, so in a 3000-actor library a selected actor could fall outside it and the download would **silently do nothing** — pinned by `GalleryTest::test_selected_actors_survive_a_narrowed_pool`.

⚠️ **`POST /gallery/plan` still has two targets** and they are the dialog's two tabs; `record` force-sets `cast = none` even if a client sends one (a still cannot tell you who is in it, so the tab's total and its download must stand on one number). Queue items carry `type: 'actor'` → `POST /gallery/cast/{id}`, so one actor's photos are never duplicated per film. ⚠️ The portrait size (`cast_size`) **and the source (`cast_source`)** must travel through the queue — `ui/queue.tsx` sends both on the actor branch; forgetting one silently downloads the default. ⚠️ `/images` needs `include_image_language=en,null` — the same trap as trailers (§9). Downloads go through `StorageMeter::storeContents()` and the quota is re-checked **per photo**: on exhaustion the fetch stops, keeps what it saved and returns **413**. ⚠️ `limit`/`per_actor` accept `0` = „none" (§3.6). ⚠️ „Make main" writes `poster_source = 'tmdb'`, never `'upload'` (the file is already counted once), and is **rejected for cast photos** (422) because `cast_members.photo_path` is a shared global column. Per-user options live in `module_user.settings` and `readGalleryDefaults()` still understands the **old** flat `limit`/`size` keys, so nobody's saved settings break.

**Routes:** `GET /gallery` (summary) · `GET /gallery/groups?by=record|actor|source|provider|module` · `GET /gallery/photos` · **`GET /gallery/module-photos`** · `POST /gallery/plan` · `GET|POST /gallery/videos`, `DELETE /gallery/videos/{galleryVideo}` · `DELETE /gallery/images/{galleryImage}` · `POST /gallery/images/{galleryImage}/primary` · `GET|POST /gallery/cast/{castMember}` · `GET|POST /gallery/{type}/{id}`. ⚠️ **Everything must stay above `/gallery/{type}/{id}`** in `routes/api.php`, or „groups"/„photos"/„videos" is read as a type. ⚠️ **Thematic categories were removed on 2026-09-11 (§4.5)** — `gallery_themes`, `gallery_images.theme_id` and the assignment routes are gone (the migration is MySQL-only; on sqlite the column and the table stay, because dropping a table whose FK still names the column makes every `insert` fail). `gallery_images.category` stays — that is TMDB's *technical* type and comes from the source.

**The gallery page's cuts (Tasks §4.1 → §8.3)** — six of them, and they are `GALLERY_CUTS`. `by=record` (**every** parent, not just TMDB domains) · `by=actor` (with a `gender=female|male` chip row) · **`by=source`** (which *domain* it came from) · **`by=provider`** (which *source* brought it — TMDB · Wikimedia · a SerpApi engine) · **`by=module`** (every other module's own images) · all photos. ⚠️ **`source` and `provider` are two different questions** and after web search both need an answer; they are deliberately not merged. ⚠️ **The source cut groups by *domain*, not by record**: a cast photo's parent is the actor (one photo, not one per film), so "did this come from a film or a series" can only be derived from **which domain that actor plays in**; an actor in both shows up in both groups and the UI says so. Its group carries `from: <domain>` with `id: 0`, and drilling in uses `?from=` instead of `owner=` — `GalleryController::sourceQuery()` is the single source for both the count and the contents, so „the group says 40, inside are 37" cannot happen. ⚠️ **The module cut is read-only** (`Services/Gallery/ModuleImages`): those are covers, thumbnails and `<module>_files` images, i.e. **part of the record** — deleting one is editing the record, not a gallery action. Its map (`RECORD_SOURCES` + `FILE_SOURCES`) is checked by `RegistryConsistencyTest::test_every_module_with_images_is_in_the_gallery_module_cut`, because a forgotten module would just vanish from the cut. ⚠️ The `note` module lives on the **private disk**, so its rows carry `private: true` and a `/note-files/{id}` URL — the flag is the backend's to state; a copy of `PRIVATE_ROOTS` in the SPA would drift and expose a private file under a public URL. ⚠️ **A group renders as a stack** through the shared **`ui/photo-stack.tsx`** (five cards since §8.6, so `groups` returns five `previews`), the very component the record page's `CastPhotoStacks` uses. ⚠️ **Per-photo info** is one function, `lib/galleryPhoto.ts::galleryPhotoInfo()`. ⚠️ **„Grouped / mixed" is a toggle, not a cut** (`gallery.layout.*`): on a record's cast sub-section it switches one-card-per-actor against one-card-per-photo, and on the flat lists `sort=new|old|random` does the same job. ⚠️ **`random` is seeded** (`?seed=`) — without a seed page 2 would repeat page 1; sqlite has no `RAND(seed)`, so there the same stable shuffle is done arithmetically.

**Web search — images & videos (Tasks §7.5/§7.6, built 2026-09-11; distribution and video saving added in §8.4)** — `Services\Serp\SerpApiClient` + `Services\Web\WikimediaImages` behind `GET /api/web/{status,images,videos,video}` and `POST /api/web/import`. ⚠️ **The route group is `/web/*`, not `/serp/*`, and the controller is `WebSearchController`** — SerpApi is only *one* source in a list. Where it is used: the actor page, a record's gallery block, a gallery group and the video form. ⚠️ **`POST /web/import` distributes across actors since §8.4**: it takes `distribute[]` (cast member ids) and assigns each photo to the first person whose name — in either language — appears in the result's title or link; everything unmatched falls back to **the record**. The rule lives on the server **once** (so it is tested and understands the Georgian name), while the client may override a single photo with `images[].target_id`; the response carries `assigned` so the toast can say where things went. ⚠️ **Matching is on names, not faces** — there is no face recognition and none will be added, which is exactly why the default is always the record: a doubtful photo lands on the film, never on a random actor. ⚠️ **One photo goes to one parent**: dedupe is per parent, so attaching the same URL twice would store two files and bill the quota twice. ⚠️ **Video search now persists** (`gallery_videos`): `GET /api/web/videos` existed but had **no caller at all**. `POST /api/gallery/videos` saves the link, the remote thumbnail, the channel and the duration — **nothing is downloaded**, so the quota is untouched (the bookmarks `og:image` rule), and `platform`/`embed_url` are derived by `VideoUrl`'s allowlist (raw HTML is never stored). ⚠️ **Safe search stays off and thumbnails are never blurred** (the user's explicit condition); there is no content-classification logic anywhere in the code and none is to be added. Nine things are easy to get wrong:
- ⚠️ **One client, one counter.** `SerpApiClient` is the only place a SerpApi request leaves from (the `StorageMeter` rule); a second path would silently desync the count. There are **two** counters and both are needed: ours (`serp_searches` rows — who, which engine, when) and the real one (`GET /account`, which **does not spend quota**, verified). The limit is enforced by both, because ours still works when `/account` is down.
- ⚠️ **`serp_searches` has no `month` column on purpose** — the plan renews on the **7th**, not the 1st, so the window moves; freezing it into a column would drift from the real number. `SERPAPI_MONTHLY_LIMIT=250` is only *our* accounting ceiling.
- ⚠️ **The cache (24 h) is load-bearing, not an optimisation** — re-opening a form or pressing back would eat the 250 in days. A cache hit **writes no row and spends nothing**, and the response says so (`spent`). **A failure is never cached**, or one flaky second reads as "unavailable" all day.
- ⚠️ **Three different empty states, and they must stay distinguishable**: quota gone → **429 `serpapi_quota_exceeded`** (registered in `lib/errors.ts`'s `CODES`), source not answering → 503, found nothing → 200 with an empty list.
- ⚠️ **The query starts from the context, not from an empty field** (§5.2): on a record it opens with the film's title and offers **that film's cast** as chips that *append* to it (a chip fills the field, it never searches — that would spend budget). The dialog also states out loud **where the downloaded photo will attach** (the record you opened it from, even if you typed an actor's name), because that is what decides which §4 group it lands in. The same dialog is now reachable from a gallery group too (§5.1).
- ⚠️ **Searching happens only on an explicit click** — never on save, sync or page load. Same reason `serpDelayMs` was *not* added: every search is its own button, so the queue's pacing setting would change nothing (a setting that does nothing is worse than none).
- ⚠️ **Wikimedia Commons is the default source** — free, **no key**, no limit, license visible in the result — so an ordinary search costs nothing. It **requires a `User-Agent`** (403 without one, verified) and its tag search is weak (it matches file name and description), which is exactly why SerpApi stays in the list. SerpApi's four image engines are `google_images_light` (the default paid one) · `google_images` · `yandex_images` (**not** `yandex`) · `yahoo_images`; `safe=off` exists only on the Google ones and the UI says so instead of quietly "protecting" the user.
- ⚠️ **Each engine names the same fact differently** and that is why the catalogue has a `query`/`results` column per engine: the query parameter is `q`/`text`/`p`/`search_query`, sizes come as `original_width` (Google) · `size.{w,h}` (Yandex) · `dimensions: "1000x1600"` (Yahoo), and on Yahoo `link` is the redirect while `source` is the page — the opposite of Google. `yandex_videos` returns rows with **no title or link**, so they are counted into `dropped` and the UI says "found, but without links" rather than "found nothing" — otherwise the search would be spent and repeated.
- ⚠️ **A dead `original` is normal** (hotlink protection), so the thumbnail is saved as a fallback and `gallery_images.is_thumbnail` says out loud that it is one. The row also carries `source_url` (the page) and `remote_path` grew 255 → **1000** chars (MySQL only). **No unique index on `remote_path`** — 1000 utf8mb4 chars is 4000 bytes, past MySQL's 3072 limit (`bookmarks.url`'s precedent), so duplicates are cut in PHP. **HTML is never stored**: the `content-type` is checked and a non-image is not downloaded (a 403 page would otherwise be saved "as a photo"). A downloaded photo **does** count against the quota (unlike TMDB's shared files) — `StorageMeter::storeContents()`, **413** on exhaustion, and what was already fetched stays.
- ⚠️ **A cast member's search tags live in their own table, `cast_member_tags`** (`unique(user_id, cast_member_id)`), never on `cast_members`: that dictionary is **global** (one actor is one row for every account), so a column there would show my tags on someone else's page and two accounts would overwrite each other. The source label is the **backend's** to write (an unknown engine becomes `web`), or the "where did this come from" filter would mean nothing.

**Gallery videos and actor details (Tasks §8.1)** — two additions that look small and are not. **`gallery_videos`** is `gallery_images`' twin: the same polymorphic parents (`videoable`), `BelongsToUser`, and rows written only by `Api\GalleryVideoController`. ⚠️ **It is a separate table on purpose.** A photo is a file (`path`, `size`, quota, disk); a video is a **link** — nothing is downloaded and the thumbnail stays a remote URL (`thumbnail_url`, the bookmarks `og:image` rule). Folding it into `gallery_images` would have made `path` nullable and forced `StoredFile` to ask „is there a file here" on every row, i.e. the quota accounting would branch on a type. ⚠️ **No `path` column** → `StorageMeter::referencedPaths()`, `UPLOAD_FOLDERS` and the orphan scan are untouched. ⚠️ **No `visibility` column** → it inherits the parent's, exactly like `gallery_images`, so `PublicDomain::DOMAINS` needs no row (and `RegistryConsistencyTest` stays happy). ⚠️ `platform`/`external_id`/`embed_url` are written in **one** place, `GalleryVideo::applyUrl()`, through `VideoUrl`'s allowlist — raw HTML/embed markup is never stored (`GameVideo`'s precedent). ⚠️ `url` has **no** unique index (1000 utf8mb4 chars is 4000 bytes, past MySQL's 3072 limit — `bookmarks.url`'s precedent); duplicates are cut in PHP. ⚠️ The model is in `AuditRegistry::MODELS` → `gallery`, and the player got a third `kind`, **`link`**: a gallery video has no row in `videos`, so counting a „watch" on it would write to somebody else's record or 404.

**`cast_members` gained the person's own facts** (`imdb_id`, `birthday`, `deathday`, `place_of_birth`, `biography`, `known_for`, `popularity`, `homepage`, `profile_links` JSON, `details_synced_at`), filled by `Services\Cast\CastEnricher` from one TMDB call (`/person/{id}?append_to_response=external_ids`) behind **`POST /api/cast/{castMember}/resync`**, and rendered by `components/ActorHero.tsx`. ⚠️ **These belong in the global dictionary** — a birthday and an IMDb id are the same for every account, exactly like `name` and `gender`; what is *mine* stays in `cast_member_tags` and in `gallery_images.user_id`. ⚠️ **`profile_links` is JSON, not five columns**: TMDB keeps adding networks (most recently `tiktok_id`) and a column per network means the next one is silently lost; the UI draws only the ones it knows and keeps the rest. ⚠️ **The biography is English-only and gets no translation table** — TMDB practically never returns a Georgian one, so the table would stay empty (the books precedent). ⚠️ **It is an explicit button, not an automatic fill on open**: the TMDB budget is shared and an actor page is opened often; `details_synced_at` records that we tried, so „we asked and there was nothing" and „we never asked" stay different facts. ⚠️ **A source failure is a 200 with `updated: false`**, not a 5xx — the page must still open (`bgg_unavailable`'s rule). ⚠️ The endpoint is called **`resync`** and not `sync` because `EnsureModulePermission::UPDATE_ENDPOINTS` knows that word — if these routes ever move into a module group, a POST would otherwise be read as `create` and an update-only user would get a spurious 403. ⚠️ **`CastMember::booted()` now deletes its gallery media** — an actor is never deleted today, but `morphs()` creates no cascade, so the day it happens every account's photos of that person would be orphaned and their quota held forever.

**Deleting a photo (§1.2, 2026-09-11)** — two different rules, and confusing them is what made „I removed one photo and the film lost its main image“ possible. **In a form** (movie/series/anime/book/game/board game/bookmark) clearing the cover is only a *mark*: the page keeps a `removePoster`-style flag and the deletion happens inside the `PUT` (`remove_poster`/`remove_cover`/`remove_image`/`remove_thumbnail`), so leaving without saving changes nothing — pinned by `GalleryTest::test_updating_a_record_without_the_remove_flag_keeps_the_poster`. **In the gallery** the delete is immediate by design (it is a library, not a form), and ⚠️ **the record's main photo is a gallery file**: „make main“ points `poster_path` at `gallery_images.path`, so deleting that photo takes the record's poster with it. `GalleryController::destroyImage()` clears `poster_path`/`poster_source` first (a dangling path would render as a broken image), and since §1.2 the confirm dialog **says so explicitly** when the selection contains the primary photo — the deletion is allowed, it just can no longer happen unnoticed.

**Translations (Tasks 7)** — `/translations` (page) + a header badge (`GET /translations/summary`). Two services: `Services/Translation/TranslationScanner` decides *what is missing* and `ItemTranslator` fills it. ⚠️ **A translation needs a source**: a record counts as translatable only when a text exists in one language and not the other — text missing in *both* is a `/sync` problem, not a translation one, and treating it otherwise would leave the header badge permanently lit. Order of sources is deliberate: **TMDB first** (free and authoritative — `details($id,'ka')`, and `TmdbClient::genreList('ka')` returns real Georgian genre names, so genres never reach Claude), then `Translator` for the remainder. `Translator` is now **bidirectional** (`translate($text,$to,$context)`, `toGeorgian`/`toEnglish`) and exposes `configured()` = has `ANTHROPIC_API_KEY`; the free Google fallback returns 429, so the UI says plainly when the key is absent. Existing text is **never overwritten**; a ka result that contains no Mkhedruli is rejected (`Lang::georgian()`), which is how "the translator handed back the original" is caught. Records go through the queue one at a time (`kind: 'translate'`), genres are one queue unit for the whole dictionary. **Videos are out of scope** — `videos.title`/`description` are plain columns with no bilingual schema. **Where a description came from is visible on the record page** (`<movie>_translations.source`: `tmdb` · `translation` · `manual`). ⚠️ **Editing a description by hand sets `source = 'manual'`** — otherwise a record kept claiming it was machine-translated after the user had rewritten it, i.e. the badge lied. ⚠️ It is only re-stamped **when the text actually changed**: merely opening and saving the form must not relabel TMDB's text as hand-written. ⚠️ The badge reports the source of **the language actually rendered** — with `ka` empty the `en` text is shown, so the `en` source is the honest one to name.

**Approvals (`approval_requests`)** — registration is open but a new account starts empty: the user asks for modules on `/modules` and a super-admin approves on `/admin`. Genres are global, so a non-admin's `DELETE /genres/{id}` returns **202 + a pending request** instead of deleting (super-admin deletes directly). **Quota-increase requests (Tasks 17.4) are the third type** (`storage_increase`, `POST /api/requests/storage`). All three share one table and `AdminRequestController::approve()`; the genre side runs through `Services/Genres/GenreRemover`, which counts/reassigns across **all** users. ⚠️ `approval_requests.type` is a **plain string, not an enum** — an enum would need a migration per type and sqlite (tests) renders it as a `check` constraint that rejects new values; the set of types lives in `ApprovalRequest::TYPE_*`. Adding a type = one constant + one handler in `approve()`. A pending request can be approved from `/requests` **or** from `/users/{id}` (Tasks 1.3) — same endpoints, and `lib/display.ts::requestLabel()` is the single label renderer for all three views.

**Storage quotas (Tasks 17.1/17.3)** — `users.storage_quota_bytes` (default 1 GB, admin-editable on `/users/{id}`) + `users.storage_used_bytes`, a **cached counter** maintained by deltas. `Services/Storage/StorageMeter` is the **single definition of what counts** (decided in Tasks §19.4, option B): **only the user's own uploads** — avatar, a *manually uploaded* poster (`poster_source = 'upload'`), video/song thumbnails, `video_files` and `gallery_images`. **TMDB posters and actor photos do not count** (shared files the user never chose). Every upload must go through `StorageMeter::storeUpload()` (guards the quota, then stores, then adds) and every delete through `deleteUpload()` / the `StoredFile` trait's `deleted` hook (`GalleryImage`, `VideoFile`) — any other path silently desyncs the counter. ⚠️ **Releasing a record's own upload belongs in the model's `deleting` hook, never in the controller** (`Movie::deletePoster()`, `Series::deletePoster()`, `Video`/`Song::deleteThumbnail()`, `Book`/`Game::deleteCover()`, `BoardGame::deleteImage()`). `PurgeService` deletes with a bare `$record->delete()` *precisely so the events fire*, so cleanup written in `destroy()` is skipped by bulk delete: until 2026-09-06 movie/series/video/song did it in the controller, which left the file on disk, kept the bytes counted forever, and made `plan()`'s "bytes freed" a lie (book/game/board_game had always done it in the model — that asymmetry is what exposed it). Pinned by `StorageManagementTest::test_deleting_a_record_releases_its_upload_at_model_level`, which deletes **through the model**, not the endpoint. ⚠️ Only `*_source === 'upload'` is released; a TMDB/RAWG/BGG/Open Library file is shared and must survive the record (a second test pins that too). Over quota returns **413 `storage_quota_exceeded`** (deliberately not 422, so the frontend can tell it from validation); `lib/errors.ts` translates that code via `errors.*` — **a new machine code must be added to its `CODES` list**, otherwise the toast shows the raw string, and `isApiCode(e, code)` is there for when the UI needs a distinct state rather than a toast (e.g. `bgg_unavailable`). `StorageMeter::files()` also backs both file lists — the admin one on `/users/{id}` and the user's own upload library, which **moved from `/settings` to `/profile` on 2026-09-11** (§6.2, `components/StorageFilesCard.tsx`) — through one shared `components/StorageLibrary.tsx`, so the two views can never disagree. ⚠️ **In that library one click selects, it does not open** (§2.9's rule); opening and downloading are separate buttons. Bulk delete rides on the *same* `DELETE /api/storage/files` with `paths[]`/`all` (one rule, one place) and goes through `StorageMeter::deleteOwnFiles()`, which snapshots `files()` **once** — a per-path loop meant one full DB+disk scan per file. `POST /api/storage/files/download` zips a selection via `StorageMeter::archiveOwnFiles()`. ⚠️ **The zip does include private-disk files and that is deliberate**: §17.5's rule is that a private file must not leave the server *without an ownership check*, and this route is behind `auth:sanctum` and resolves every path inside that user's own `files()`. The per-file download button still stays hidden for private files — it points at `/storage/*`, which has no auth. ⚠️ **Each row carries `private`** (`StorageFolder::isPrivate($path)`), because `/storage/*` cannot reach the private disk: without it the page drew a broken `<img>` and a 404 download link for every note attachment, chat media and `<module>/fields` upload (fixed 2026-09-06). The flag is the **backend's** to state — a copy of `PRIVATE_ROOTS` in the SPA would eventually drift and expose a private file under a public URL. Private rows render a lock icon and get no download button; downloading them stays in each section's own ownership-checked route. Each row carries `owner_type`/`owner_id`, which is how **`DELETE /api/storage/files`** routes a single delete (`StorageMeter::deleteOwnFile()`: clear the column or drop the `video_files`/`gallery_images` row); it looks `path` up **inside that user's own `files()`**, so another account's file — and any shared TMDB poster — is a 404 by construction. **Orphan cleanup (`GET|POST /api/storage/orphans[/clean]`) is global, not per-user** and therefore `super_admin`-only: uploads share folders, so a file nothing references has no owner left. It scans only `StorageMeter::UPLOAD_FOLDERS` (recursively — see the folder table above) and skips anything touched in the last hour (an upload may still be in flight). ⚠️ **Every new upload column must also be listed in `StorageMeter::referencedPaths()`** — anything missing there is classified as an orphan and *deleted* by the admin's cleanup. `games.cover_path` and `game_files.path` were missing from 2026-09-04 until it was caught the same day; `note_entry_files.path` was added with the module and `messages.attachment_path` with chat media (§16.3). **Increase requests (17.4)** ride on `approval_requests` (see *Approvals* above): the user asks on `/settings`, an admin applies it from `/requests` or `/users/{id}`. ⚠️ `payload.requested_bytes` is the **desired total quota, not a delta** — a delta would compound if two requests were approved; `granted_bytes` lets the admin hand out less than asked without it counting as a rejection. **Per-module allocation (17.2) is live**: `module_user.storage_limit_bytes` (nullable) + `PUT /api/storage/allocations`, edited on `/settings` (`components/StorageAllocations.tsx`). ⚠️ `null` means *no dedicated limit* (the module draws from the shared pool) while `0` means *uploads blocked* — that is why the column is nullable and why the API takes `null` to clear. The sum of all limits may not exceed the account quota (checked **before** writing, 422 `allocation_exceeds_quota`). ⚠️ **No upload site needed changing**: the module is derived from the folder (`StorageFolder::moduleFor()`), which `storeUpload()`/`storeContents()` already receive — but that map **must agree with the `module` field in `files()`**, or an upload would be counted against one module and checked against another's limit. Over a module's limit returns **413 `module_quota_exceeded`** (a separate code from `storage_quota_exceeded`: the user still has room overall, they capped this module themselves). ⚠️ Shrinking a limit below what is already used **never deletes files** — it only refuses new uploads. Pre-flight estimates (17.3) are **not needed for `/sync`** — it only fetches TMDB media, which 19.4/B excludes from the quota — they matter only for the gallery (§10).

**Bulk delete (Tasks 20)** — `/purge` + `Services/Purge/PurgeService`, `super_admin` only. ⚠️ **The most destructive code in the project.** Three rules hold it together: the scope is always **explicit** (`mode` + params; `all` is its own mode, so an empty filter can never mean "everything"), `plan()` and `run()`/`runOne()` share one query so *counted* and *deleted* cannot drift, and deletion always goes **through the model** (never `delete()` on a query) so the `deleting` events fire — files, quota counter and polymorphic pivots. `target = 'gallery'` deletes only the photos and keeps the records. **Which scope fits which target is one table, `PurgeService::TARGET_MODES`** (mirrored on the frontend as `PURGE_TARGET_MODES` in `api/account.ts`), and statuses are per-domain too, so `status=read` on a movie is a **422 `invalid_status`** instead of a silently empty scope. ⚠️ **Since §6.4 the status list is read through `PurgeService::statusesFor($target, $userId)`, not straight off `TARGET_STATUSES`**: six domains have a per-user dictionary, so the valid keys are **the target account's** — `/purge` deletes somebody else's library, and checking their renamed „watched“ against *my* defaults would 422 a perfectly good request. `TARGET_STATUSES` survives as the built-in fallback (a film is `watched`, a book `read`, a board game `owned`, a note `done`) and `RegistryConsistencyTest` pins it against `StatusDomain::defaultKeys()`. Adding a module = one row in each of the four maps (`TARGET_MODES`, `TARGET_STATUSES`, `SECTION_TABLES` for its `<module>_files`/`<module>_notes` — the notes model may be `null`, as `note` has files but no attached-notes table, `UPLOAD_COLUMNS` for the metered upload column — `note` has none) + the model in `modelQuery()`/`morphAlias()`. ⚠️ The `type` mode reads a **different column per domain** (`type_id` on video, `category_id` on note, `genre_id` elsewhere, a pivot on game) — it is one `match`, not an `if`. On the frontend the same two facts live in `PurgePage`'s `DICTIONARIES` and `STATUS_NAMESPACE` maps; a module missing from them silently renders an **empty** type list or a raw i18n key (that is what happened to `game` until 2026-09-04). ⚠️ `keep_favorites` is applied to **every** target, so the checkbox is shown for every target — it used to be hidden on video/song/gallery while still being sent. The UI is a two-step: plan → typed `DELETE` confirmation → **per-item queue** (`enqueuePurge`, queue kind `purge`), one short `POST /admin/purge/item` per record, so progress shows and `artisan serve` never blocks. `plan.items` is the queue; on the gallery target it lists **only records that actually have photos** (`galleryOwnerIds()`) — a cast photo counts for every record that actor appears in, so the second record legitimately reports "skipped". An id outside the target account is a **200 + `skipped`**, not an error: one bad id must not break the loop.

**Audit log (Tasks §4)** — `/audit` + `audit_logs`, built 2026-09-10. The requirement was literal: "everywhere, absolutely every module, full logging". ⚠️ **`Services/Audit/AuditLogger` is the single write point** and `Observers/AuditObserver` feeds it — the observer is attached in **one loop** in `AppServiceProvider::boot()` over **`App\Support\AuditRegistry::MODELS`**, so no controller contains logging code and no module can be forgotten. Adding a model to the log is **one row in that map**; `RegistryConsistencyTest` now fails if a `modules` row has no model there. Eight things are easy to get wrong:
- ⚠️ **`moduleFor()` asks the model first (`auditModule()`), then the map** — `Status` is one table serving six modules (`statuses.module`), so a static class→module row would file every status change under one section and the log's module filter would never find it.
- ⚠️ **`AuditRegistry::typeFor()` must not call `getMorphClass()`** — `enforceMorphMap()` *throws* for a model outside the map, and most logged models (`Module`, `Role`, every `<module>_files`) are outside it. The map is read directly (`Relation::morphMap()`), falling back to snake_case.
- ⚠️ **`labelFor()` reads raw attributes only**, and consults accessors solely when their relation is *already loaded*. `Movie::$title_ka` sits on the `translations` relation: reading it inside the `created` event **cached an empty collection** on the model, and the real title became unreadable afterwards. Logging must never mutate what it logs.
- ⚠️ **`AuditLogger::$tableExists` memoises only `true`.** A `false` memo silently disabled logging for the whole process whenever something asked before the migration ran (`migrate:fresh`, the test bootstrap, the first request of a deploy) — which is exactly how the first version shipped broken.
- ⚠️ **`update` logs only the keys that actually changed** (`getChanges()`, `updated_at` stripped), with both sides under the same keys — that *is* §4.1's "old and new side by side". A `touch()`-only change writes nothing.
- ⚠️ **"Which section did they enter" comes from the SPA** (`lib/audit.ts` → `POST /api/audit/visit`), not from middleware: in an SPA a section change is a route change, not an HTTP request — one page fires five GETs and the browser's Back button fires none. Repeats inside a one-minute window are dropped server-side (`AuditLogger::visit()`), and the module is derived from `modules.route_base`, never a second hand-written list.
- ⚠️ **`admin:audit` is the fourth `Role::ADMIN_RESOURCES` entry** (mirrored in `RolePage`'s `ADMIN_RESOURCES`), so viewing and cleaning are separate rights — `EnsureAdminAccess` derives `view` from GET and `delete` from DELETE. That is also why **`GET /admin/audit/plan` is a GET**: as a POST the middleware would read it as `create` and a view-only role would get a spurious 403.
- ⚠️ **`AuditLog::PROTECTED_ACTIONS` (`chat_delete`) survives the cleanup** (§4.7's rule). The deleted message itself lives on in `messages`, but *who deleted it, when and how* exists only in the log, so wiping it would leave the recovery possible and the accounting gone. `plan()` reports the protected count separately so "I selected 100, 97 were deleted" is never a mystery.
- ⚠️ Cleanup (§4.7) shares `filtered()` with the list, and `ids` **narrows** the filter rather than replacing it — a selection can never reach outside what was shown. `confirm: "DELETE"` is required, `purge`-style.

**Chat message deletion (Tasks §4.5/§4.6)** — `DELETE /api/chat/messages/{message}` with `scope=self|both`. ⚠️ **The row stays in the database** (recovery), so this is hiding, not deleting: `messages.removed_at`/`removed_by`/`removed_scope` + `Message::scopeVisibleTo($userId)`. ⚠️ **The column is deliberately not called `deleted_at`** — that name is `SoftDeletes`' contract, and if anyone added the trait later every query would silently filter, including "deleted for me only", which the *other* side must still see. ⚠️ **`scope` has no default**: asking the question is the feature (the old behaviour always deleted for both). ⚠️ **`both` requires authorship**; hiding for yourself is anyone's right since it only touches your own view. ⚠️ **The file stays on disk and on the sender's quota** — it is part of the recovery; freeing space is the separate, explicit `DELETE /api/chat/files/{message}`. Removed messages also stop counting as unread (`ChatService::unreadCounts()`) and drop out of the conversation list's "last message", which is per-viewer for the same reason.

**Public profiles (Tasks §16.1)** — `/u/{username}`, backed by `GET /api/public/profiles/{username}` and `GET /api/public/profiles/{username}/{domain}`. ⚠️ **These two are the only domain endpoints outside `auth:sanctum`** — "public profile" means a shareable link, so requiring a login would make it something else. The whole mechanism switches off with one env var: `PUBLIC_PROFILES=false` (`config/mediary.php`) makes `PublicProfileService::resolve()` return `null`, so every public endpoint 404s without touching anyone's settings. **Three layers must all be open** for a record to appear, each `private` by default: `users.profile_visibility` → `module_user.is_public` → `<record>.visibility`. **All three layers are edited on `/profile` since 2026-09-11 (§6.1)**: `components/PublicProfileCard.tsx` holds layers 1+2 (both toggles **save immediately** — an unsaved visibility switch is a dangerous misunderstanding) and now embeds `components/VisibilityManager.tsx` for layer 3 — domain chips, search, an all/public/private cut, pagination and bulk switching, backed by `GET /api/visibility/{domain}` and `PATCH /api/visibility/{domain}`. ⚠️ **The per-record toggle is gone**: `VisibilityToggle.tsx` now exports only `VisibilityBadge` (the record still *shows* its state, it just isn't changed there) — one fact managed in two places is what made "where is this setting" a guessing game. ⚠️ The list reuses `PublicDomain::card()` rather than each module's `index`: nine domains need one narrow shape, and it is the same one the public profile draws. ⚠️ **`all: true` is an explicit scope** and an empty selection is a **422**, never "everything" (`PurgeService`'s rule); another user's id in `ids[]` is silently skipped, not an error. Five things are easy to get wrong:
- ⚠️ **`withoutGlobalScope('owner')` + an explicit `user_id` is mandatory** in `PublicProfileService::query()`, and the reason is two-sided: unauthenticated, `BelongsToUser`'s `owner` scope does **nothing** (every user's rows would come back); for a logged-in visitor it would cut to **their own** library (someone else's profile would look empty). Both directions are pinned by `PublicProfileTest`.
- ⚠️ **A bookmark's identity is its own `url`** (`PublicDomain::MATCH`) — there is no external dictionary for links, but a URL is already a global key, so two people who saved the same page do match.
- ⚠️ **`note` can never be public** (§16.5's strict rule — that module holds private documents). It is absent from `PublicDomain::DOMAINS`, so `module_user.is_public = true` has no effect and `PUT /modules/note/public` returns **422 `module_not_shareable`**. The `visibility` column on `note_entries` still exists; it just can't surface anything.
- ⚠️ **The public card is a narrow hand-rolled shape** (`PublicDomain::card()`), *not* `MovieResource`/`BookResource`/… . Those return the full record (`sync_status`, `ge_url`, my progress, file counts) and one new field added later would silently leak to strangers. Here a field appears only when it is written explicitly.
- ⚠️ **`playlist` is a domain but not a module** — it lives inside `song` (§15). That is why `App\Support\PublicDomain` exists as its own map instead of leaning on `modules.key`, and why `VisibilityController` does its own `hasModule()`/`hasPermission()` checks rather than using `module:@type`/`permission:@type` middleware.
- ⚠️ **One endpoint covers all nine domains**: `PATCH /api/visibility/{domain}/{id}` (the `/media/sync/{type}/{id}` pattern), not eight per-module routes. `PATCH` deliberately — `EnsureModulePermission` derives `create` from POST. A non-public profile is **404, not 403**: "this user exists but is hidden" is itself information. Admin force-private (Tasks 1.3) rides on `PATCH /admin/users/{user}` → `profile_visibility` and is deliberately two-way.

**Matching (Tasks §16.2)** — `GET /api/matches/{username}` (per-domain counts + similarity) and `GET /api/matches/{username}/{domain}` (the shared records, with both sides' status/rating), rendered as the "matches" tab on `/u/{username}` (`components/MatchPanel.tsx`). **`GET /api/matches` (no username) is the "similar taste" catalogue** — every public profile ranked by similarity, with `?q=` search over username/name — rendered on **`/people`** (`pages/PeoplePage.tsx`, sidebar link). ⚠️ It is a **catalogue as well as a ranking**: profiles with *zero* shared records stay in the list (§16.2 asked for "search/catalogue of public profiles", which §16.1 never had) — they just sort last. ⚠️ `MatchService::MAX_PROFILES` (50) caps how many profiles one request compares: the comparison is **exact, not approximate**, so it grows linearly; past the cap the response carries `truncated: true` and the page says so rather than pretending the list is complete. **When 50 stops being enough, the fix is a cache keyed on a content stamp** (row count + `max(updated_at)` per user/domain), *not* a TTL — a TTL would keep counting a record for minutes after it was made private. ⚠️ Unlike the public profile these are **inside `auth:sanctum`** — a comparison needs a second side and that is the current user. **Both profiles must be public**; if the caller's is not, the answer is **409 `profile_not_public`** (a distinct state, not an empty result), because the comparison is symmetric — computing it from the caller's private rows would hand the same number back to the other side. Four things are easy to get wrong:
- ⚠️ **"the same record" is one map, `PublicDomain::MATCH`**: `tmdb_id` (movie/series), `rawg_id` (game), `openlibrary_id` (book), `bgg_id` (board game), and the **pair** `platform`+`external_id` (video/song — the same id on a different host is a different thing). A null identity column means the record **does not take part** in matching at all.
- ⚠️ **„Done“ is asked in exactly one place, `PublicDomain::isDone()`** — because two mechanisms now run side by side (§6.4): the six dictionary domains answer with `role === 'done'`, while game/book/board_game still compare an enum key (`finished` / `read` / `owned`). Writing that `if` twice is precisely what would drift. `PublicDomain::countsDone()` answers the other half: **song has no status at all**, so its `both_done` is `null` ("not counted"), never `0` ("zero matched") — video used to be in that group and no longer is.
- ⚠️ **`playlist` is deliberately not matchable** even though §16.2 listed it: two users' identically named playlists are not the same object and there is no external dictionary for a song list. Its contents already match through the `song` domain.
- ⚠️ **Both sides go through `PublicProfileService::query()`** — the same three-layer query that feeds the public profile. A separate "matching query" is deliberately not written: two sources would drift and one of them would eventually let a private row through. **There is no cache** (§16.2 asked for one): this is not a cross-user join over full tables but two narrow reads of each side's *public* rows via the new `(user_id, visibility)` index, and a TTL cache would keep counting a record for minutes after it was made private. Revisit when one account has thousands of public records — and then key the cache on a content stamp, not on time alone.

**Field builder** — which fields a module's form shows. **Since 2026-09-11 (§6.5) the catalogue holds *every* field of every form, not just the optional ones.** (Its design doc was deleted 2026-09-07; everything load-bearing is in this paragraph.) Storage is `module_user.settings['fields']` (no migration); API `GET|PUT /api/modules/{key}/fields`; UI is a "Fields" section on `/modules/{key}`. ⚠️ **Only overrides are stored** — the built-in catalogue lives in code (`App\Support\FieldCatalog`), so a field added there appears for every account automatically and a removed one disappears without leaving junk. ⚠️ **Structurally mandatory fields carry a `locked` flag** (a video's/song's/bookmark's `url`, every module's title): they are listed — so the editor no longer lies about being "the module's fields" — but their `enabled`/`required`/`public` switches are disabled, and that is enforced in **`FieldCatalog::for()` itself**, not just in the UI, so a hand-written `PUT` cannot turn off a title either. (Until §6.5 such fields were simply absent from the catalogue; that was stricter but made the editor show a fraction of the form.) ⚠️ **A newly added catalogue entry defaults to `enabled = true`** (`FieldCatalog::defaults()`), or adding a field in code would change nothing until every user found the toggle. ⚠️ **There is no ordering UI any more** and `PUT /modules/{key}/fields` no longer accepts `sort_order` — the order is the catalogue's, i.e. the code's. Custom fields keep their own ordering, because nothing else defines it for them. ⚠️ An unknown key in `PUT` is **ignored, not 422** (the catalogue changes; an older SPA must not break), and writing fields **must not clobber the rest of `settings`** — gallery options and note channels live in the same JSON blob. **Phase 2 (2026-09-06) adds labels/placeholders (ka+en), `required` and ordering.** The form side is `lib/fields.ts` → **`useModuleFields(moduleKey)`** (`shows` / `required` / `label` / `placeholder` / `isMissing`) — the single place a label is resolved. ⚠️ **The default label lives in i18n, not in the backend** (`fields.name.<module>.<key>`): an un-overridden label comes back as `null` so the SPA falls back to the translated string, and **an empty input clears the override** rather than writing an empty label. ⚠️ **`required` is form discipline, not a schema constraint** — the field is in the catalogue precisely because the column is nullable, so the backend does *not* enforce it. Its label was renamed in §6.5 ("don't save it empty") because "required field" read as a database rule. ⚠️ **An unknown field key is treated as visible**, so a form that hasn't been wired up yet never silently loses inputs. ⚠️ **Only add a catalogue entry once the form actually honours it** — a toggle that changes nothing is worse than no toggle. **Every form is wired, and since §6.5 for every one of its fields** — roughly 100 catalogue entries across the nine modules (title/url/status/genres/cover/description/… , not just the handful of optional extras it started with). Each one honours `fields.shows()` / `fields.required()` / `fields.label()` / `fields.placeholder()`, so the label override typed in the editor actually reaches the form. ⚠️ `movie` and `series` share one form but get **separate** catalogue entries — the config is per-module, so hiding a field on series must not hide it on movies. Widening the list is cheap: one row in `FieldCatalog` + `shows`/`label`/`required` in the form + two i18n labels. **Phase 4a (per-field public flag) is live too**: a field with `public: false` is dropped from `PublicDomain::card()`. ⚠️ The **record owner** decides, never the viewer — `PublicProfileController` reads the owner's config and `MatchService` reads *the other side's*, because the card is theirs. ⚠️ `id`/`domain` are never hidden (the card can't render or link without them). ⚠️ **Every new field attribute must also be added to `ModuleController`'s validation rules** — `validate()` returns only validated keys, so an unlisted attribute drops the whole `fields` array from the payload and the `PUT` 500s (this actually happened with `public`). **Phase 3 (custom fields) is live since 2026-09-06** (`docs/DECISIONS.md` §2, answer "a separate table"): a definition lives in `module_user.settings['custom_fields']` (it belongs to the module) and its **value** in `<module>_field_values` (it belongs to the record) — one table per module, `CustomFields::TABLES`. ⚠️ Adding a module means adding its `<module>_field_values` table **in that module's own migration, behind a `Schema::hasTable()` guard** (`bookmark` does this): the two 2026-09-06 migrations iterate `CustomFields::TABLES`, so on a fresh database they already create it, while an existing database needs the new migration to. ⚠️ **Nine tables, one controller** (`CustomFieldController`, `{module}` param — the `/visibility/{domain}/{id}` pattern): `GET|PUT /api/modules/{key}/custom-fields` (whole list; removing an entry deletes it) and `GET|PUT /api/custom-fields/{module}/{id}` (values). ⚠️ **The value is split into typed columns** (`value_text`/`value_number`/`value_date`/`value_bool`) — in one text column a number would sort alphabetically (`"10" < "9"`), losing exactly what the table was chosen for. ⚠️ **A key never changes**: renaming edits the label, since the key is what ties the stored values to the field. ⚠️ **Deleting a definition deletes its values**, or the same name later would resurrect old answers. ⚠️ **An empty value deletes the row** — "not filled in" and "empty text" are the same thing. ⚠️ `components/CustomFieldsCard.tsx` **saves itself** (values never travel in the record's `PUT`, so none of the seven forms changed their save path) and its button is `type="button"`, or it would submit the parent form; on an unsaved record it shows a hint instead of inputs, since a value needs a `record_id`. ⚠️ **A custom field never reaches the public card** and gets no `public` toggle — `PublicDomain::card()` is a narrow hand-built shape. ⚠️ The built-in field list on `/modules/{key}` **filters customs out** (`PUT /modules/{key}/fields` ignores unknown keys, so a switch there would do nothing); they have their own editor, `CustomFieldsEditor`. **Phase 4b (the `file` type) is live since 2026-09-06, so §6 is complete.** The value stays in the same row — four new columns (`value_path`/`value_name`/`value_mime`/**`value_size`**) — and the endpoints are `POST /api/custom-fields/{module}/{id}/file` + `GET|DELETE .../file/{key}[/{file}]`. **A `file` field takes up to `CustomFields::FILE_MAX_COUNT` (10) files since 2026-09-11 (Tasks §7.3)**, and five things about that are easy to get wrong:
- ⚠️ **The row is still one file; multiplicity is a schema change**, not a form one. `<module>_field_values` gained `sort_order` and the unique index went `(record_id, field_key)` → `(record_id, field_key, sort_order)`. **Dropping the index instead would have let every other type hold two answers too** — a text field with two rows, silently picked up by `values()`. A non-`file` row always sits at `sort_order = 0`, so for it the index is exactly as strict as before (and `setValues()` therefore pins `sort_order` in its `updateOrInsert` match).
- ⚠️ **On MySQL the new index must be created before the old one is dropped.** `record_id` has a foreign key and MySQL was using the old unique's leftmost prefix for it, so the drop fails with *"Cannot drop index … needed in a foreign key constraint"* — this actually happened on the first run. The migration also checks `hasColumn`/`hasIndex` **per step**, because that failed run left the column added and the index unchanged, and a single combined guard would have skipped the table on retry.
- ⚠️ **A file field's value is always a list, even with one file** — a shape that changes with the count would force an `Array.isArray()` check at every use, and one of them would eventually be forgotten. Each entry carries an **`id`**: names are not unique, so "delete this one" cannot be said otherwise.
- ⚠️ **`{file}` is optional on both the GET and the DELETE**, so the old single-file URLs still behave as they did (serve the first / clear the whole field).
- ⚠️ **Retyping away from `file` now deletes every row of that field**, not just the first. With one file that was a single empty row; with several it would leave `sort_order > 0` junk that nothing reads and that a later write would have to step around. ⚠️ **The upload is a separate endpoint on purpose**: the card sends the whole draft, so a `file` key travelling in the values `PUT` would be read as an empty value and an ordinary "save" would silently delete the file — `setValues()` therefore skips type `file` outright. ⚠️ **No new disk root**: the file lands in the module's own root (`movies/fields`, `videos/fields` — `StorageFolder::customFields()`), which is what keeps §17.2's per-module limit, the recursive orphan scan and `notes/fields` landing on the **private** disk all working unchanged. ⚠️ It is served **only** through the API route on **both** disks (the frontend reuses `PrivateImage`/`PrivateFileLink`) — two different paths would eventually put a private file behind a public URL. ⚠️ **`HasCustomFields` (on all nine models) is mandatory**: the SQL cascade that was enough in phase 3 fires no model event, so the file on disk and the quota counter would leak on record deletion. ⚠️ **Changing a field's type away from `file` deletes the file too** — for other types a stale value is merely unread, but a file would sit on disk, inside the quota and unreachable. ⚠️ **`value_size` is what gets released**, never the size read off disk (the `StoredFile` rule). ⚠️ The path must be in **`StorageMeter::referencedPaths()`** (it is, sourced from `CustomFields::TABLES`) or the admin's orphan cleanup deletes live files. Caps live in `CustomFields::FILE_MAX_KB` (25 MB) / `FILE_MIMES`.

**Chat (Tasks §16.3/§16.4)** — `/chat` (+ `/chat/:id`), `GET|POST /api/chat/{conversation}` and friends; rules live in `Services/Chat/ChatService`. Three tables: `conversations`, **`conversation_user`** (participants **and each side's `last_read_at`**) and `messages`, plus `user_blocks`. ⚠️ **Participants are a pivot, not `user_one_id`/`user_two_id` columns** — two columns turn every query into `where(a) orWhere(b)` and leave nowhere to put "read", which is per side. ⚠️ **`BelongsToUser` is deliberately not used**: its `owner` scope assumes one owner, while a conversation has two — access is decided by **participation**, checked explicitly, and someone else's conversation is a **404** (that it exists is itself information). ⚠️ **Writing requires both profiles to be public** (409 `profile_not_public`) — the same gate as matching. ⚠️ **A block stops messages in *both* directions** (403 `chat_blocked`): blocking is one-sided, but restricting only the blocker would let the blocked person keep writing to the very person who blocked them. ⚠️ **Your own message never counts as unread**, or the badge would light up the moment you sent it. Delivery is **polling** (thread 5s, list 15s, badge 30s) — no worker, as §16.3 specified. **Media is live since 2026-09-06** (`docs/DECISIONS.md` §1 answered "disappears for both"): `POST /api/chat/{conversation}` takes a `file` on the **same** endpoint (its presence picks text vs. upload, so the block/public gate is written once), `GET /api/chat/files/{message}` serves it and `DELETE /api/chat/files/{message}` removes it. Five things are easy to get wrong:
- ⚠️ **`chat/` is a private root** (`StorageFolder::PRIVATE_ROOTS`) — a private conversation's image must not open through `/storage/*`, so the file leaves the server only through the participation-checked `file()` route (404, not 403, for a stranger).
- ⚠️ **The sender's quota pays** (§16.4) — the upload goes through `StorageMeter::storeUpload()`, so exhaustion returns **413** while text and emoji still send (they never touch the disk).
- ⚠️ **"file deleted" is not a column.** A media message can never be created without a file, so `type ∈ MEDIA_TYPES` + empty `attachment_path` *is* the deleted state (`Message::attachmentDeleted()`). A flag would say the same thing with a migration and two sources that could disagree.
- ⚠️ **Only the author may delete** — the file is on their quota, so a recipient's button would silently free someone else's space. `StorageMeter::deleteOwnFile()`'s `message` branch does the *same* thing (clear the columns, keep the row) so the storage page and the chat can't disagree.
- ⚠️ **Deletion releases the recorded `attachment_size`, not the size read off disk** — the same rule `StoredFile` follows. In tests `UploadedFile::fake()` reports a different size than it writes, and subtracting the disk value silently desynced the counter.
- ⚠️ In the storage breakdown chat is the pseudo-module **`chat`**, alongside `account`: it has no `modules` row, so it can't take a per-module allocation and draws from the shared pool. Both `SettingsPage` and `StorageLibrary` special-case the two keys.

**Settings** — `frontend/src/lib/settings.tsx` (`SettingsProvider` + `useSettings()`) persists per-user in `users.settings` (`PUT /api/auth/settings`) with localStorage as a local cache and as the one-time migration source from the old single-user state. **Two levels exist**: account-wide `users.settings`, and per-module `module_user.settings` (`PUT /api/modules/{key}/settings`) — the latter also stamps `enabled_at` on first write, since a super-admin may have no pivot row at all.

Used by `MovieCard`, `MoviePage`, `LibraryPage`, `GenreSelect`, `MovieMultiSelect`, `GenreItemsManager`, `DiscoverModal`, `ActorPage`, `VideosPage`, `Sidebar`. ⚠️ `ContentLangToggle.tsx` was **deleted on 2026-09-12** — content language comes from settings, not a per-card toggle, and nothing had imported it since 2026-09-03.

CLI has no `Auth::id()`, so it falls back to `w500`. ⚠️ **Dates go through `lib/dates.ts` (`useDateFormat()`), never a bare `toLocaleDateString()`** — seven call sites each followed the browser locale, so two formats could appear on one page and the setting changed nothing. `iso` uses `sv-SE`, not `toISOString()`, which would shift to UTC and show yesterday during Tbilisi's night hours.

## Gotchas

- **PHP cURL has no CA bundle on Windows** → HTTP calls use `->withOptions(['verify' => storage_path('cacert.pem')])` (bundle committed at `backend/storage/cacert.pem`). Keep this on any new outbound `Http` call (TMDB, images, future Claude).
- **Frontend updates use `POST` + `_method=PUT`** (multipart-safe method spoofing) — see `updateMovie` in `api/movies.ts`.
- **Genres are keyed by `slug`** across manual entry and TMDB sync, so `firstOrCreate(['slug' => …])` (not by `tmdb_id`) avoids duplicate-slug violations.
- **`imdb_id` is unique per user**, not globally (`unique(user_id, imdb_id)`) — two accounts must be able to add the same film.
- **Never name a column `hidden`** (or `visible`, `casts`, `attributes`, `table`, `connection`…): those are protected properties on `Model`, so `$model->pivot->hidden` read from *inside another Model subclass* returns the protected array, not the column — silently, no error. `module_user.is_hidden` and `module_user.is_public` are named that way for this reason.
- **`/storage/*` is public, so a public profile's images are already reachable by URL** — that is consistent (a photo inherits its parent's visibility, §10) but it means making a record private does **not** un-publish an already-shared image URL. ⚠️ This still holds for posters and gallery photos **on purpose**: they are TMDB's public images and the public profile renders them. Only the `note` module moved to the private disk (§17.5) — see the disk rule below.
- **Tests run on sqlite `:memory:`** (`phpunit.xml`), which has no FULLTEXT and no `ALTER … MODIFY`: those migration statements are wrapped in a `getDriverName() === 'mysql'` check. Keep new MySQL-only DDL guarded the same way.
- ⚠️ **The cross-cutting maps are pinned by `RegistryConsistencyTest`** (added 2026-09-06; it also checks `AuditRegistry::MODELS` since 2026-09-10). Adding a module means writing it into several registries, and forgetting one is *silent* — it has bitten twice (`games.cover_path` missing from `referencedPaths()` meant the admin's orphan cleanup **deleted live files**; `game` missing from the frontend `DICTIONARIES` made `/purge` render an empty type list). The test derives its expectations from **the schema**, not from a hand-written list: every column whose name contains `path` must appear in `StorageMeter::referencedPaths()` (or in the test's `NOT_DISK_PATHS`, where only `gallery_images.remote_path` sits — it is TMDB's path, not ours), every `modules` row must be a purge target, every target with a `status` mode must have a status list, every table with a `visibility` column must be a `PublicDomain` domain (only `note_entries` is excluded, per §16.5), every `StatusDomain` entry must actually be wired (the `HasStatus` trait, a `status_id` column and a `status` purge scope — forgetting one leaves records with no status or a filter that silently returns nothing) and `PurgeService::TARGET_STATUSES` must match `StatusDomain::defaultKeys()`, and **every purge target except `gallery` must have a `DashboardController::COUNTERS` entry** (added 2026-09-07 — `note` had been missing since §13, so its dashboard card silently rendered `count: null`, and `bookmark` was heading the same way). ⚠️ It reads the `referencedPaths()` map **out of the source**, so it asserts three anchor entries first — a parse broken by a future refactor must fail loudly instead of passing vacuously. ⚠️ It earned its keep again with `anime` (§7.1, 2026-09-11), catching `animes.poster_path` and `CustomFields::model('anime')`. ⚠️ **The two 2026-09-06 custom-field migrations now skip a table whose parent does not exist yet**: `CustomFields::TABLES` keeps growing and a module added later (`bookmark` 09-07, `anime` 09-11) sits *after* them, so on a fresh **MySQL** database they were pointing a foreign key at a missing table — sqlite swallowed it, MySQL would not. That table is created by the module's own migration, behind `Schema::hasTable()`. **On the frontend the same job is done by types, not tests**: `PURGE_TARGET_MODES` is `as const satisfies …`, and `PurgeTargetWithType`/`PurgeTargetWithStatus` compute which domains *must* appear in `PurgePage`'s `DICTIONARIES`/`STATUS_NAMESPACE` — those maps are no longer `Partial`, so a new module without a dictionary fails `tsc`.
- **`/storage/*` is served without auth, so there are now two disks** (§17.5, 2026-09-05). `App\Support\StorageFolder::PRIVATE_ROOTS` is the **only** place that decides which: `notes/` and `chat/` (§16.3) → the `private` disk (`storage/app/private-uploads`, no `url()`, not reachable via `/storage/*`), everything else → `public`. Nothing else may name a disk — `StorageMeter::disk()`, `StoredFile::deleteFile()` and the orphan scan all ask `StorageFolder::diskFor($path)`, because one forgotten hardcoded `'public'` writes a private document to the world-readable disk. **A private file leaves the server through exactly one route** (`GET /api/note-files/{id}` → `NoteEntryFileController::show()`), which checks ownership explicitly and answers **404, not 403**, for someone else's file. ⚠️ Adding a private section = one entry in `PRIVATE_ROOTS` + its own policy-checked serving route (chat did exactly this in §16.3).
- **`module_user.settings` is a JSON string column**, written via `syncWithoutDetaching` with `json_encode`. Don't assume Eloquent casts it for you on the pivot.
- **Tags on videos, songs, books, notes and bookmarks are a plain `tags` JSON array**, not a table. Duplicates are stripped case/whitespace-insensitively on **both** sides — `dedupeTags()` in the form (which also toasts) and **`Video::normalizeTags()`** on save. Keep both: the form message is the UX, the model is the guarantee. `Video::normalizeTags()`/`tagKey()` are the one source used by the form save path, `POST /videos/bulk` **and `Song`/`Book`/`NoteEntry`** (which delegate to them), so tag comparison stays identical everywhere. ⚠️ Normalization lives in the **controller**, not in a model mutator — creating a record straight through `Model::create()` (a script, a seeder) will *not* dedupe.
- **`permission:@type` resolves the module from the *route* parameter first, then input** — same order as `EnsureModuleEnabled`. It used to read input only, so `/media/sync/series/5` silently checked the **`movie`** permission (fixed 2026-09-03, covered by `TranslationTest`). A shared `{type}` endpoint that carries the domain in the URL relies on this.
- **A POST that edits existing records needs its last path segment in `EnsureModulePermission::UPDATE_ENDPOINTS`** (`resync`, `watched`, `played`, `visited`, `bulk-status`, `bulk`, `reorder`, `primary`) — otherwise the permission middleware derives `create` from the HTTP method and a user with update-but-not-create rights gets a spurious 403.
- **`react-select` is used for multi-selects** (`TagSelect.tsx`, `GenreSelect.tsx`) with shared styles in `lib/selectStyles.ts`. ⚠️ The Radix `ui/multi-select.tsx` was **deleted on 2026-09-12** — nothing imported it, and a second multi-select sitting in `ui/` is exactly what a new page picks up by mistake. `MovieMultiSelect`/`IdMultiSelect` are a different file and very much alive.
- **Path alias** `@/` → `frontend/src` (no `baseUrl`; `paths` only, per the TS version). Radix component wrappers live in `src/components/ui`.
- ⚠️ **A missing translation key fails silently** — i18next just prints the key, so neither `tsc` nor ESLint notices. That is how 562 of 980 keys ended up missing and pages showed raw `roles.title` / `purge.title` (fixed 2026-09-06; both locales now hold 1487 keys and are in sync). **Run `python frontend/src/i18n/audit.py` after adding UI strings** — it reports missing keys, empty dynamic prefixes (`` t(`a.b.${x}`) ``) and any ka/en drift, and exits non-zero when something is off. ⚠️ Add every key to **both** `ka.json` and `en.json`; the audit treats one-sided keys as a problem. Locale files are plain 2-space JSON **with CRLF endings**, so a small Python script that loads → merges → `json.dumps(..., ensure_ascii=False, indent=2)` round-trips them byte-identically — but it must write with `newline='\r\n'`, or the whole file shows up as changed.
- ⚠️ **The audit has two more checks since 2026-09-07 (Tasks §1.4), and both found real bugs.** (1) **A key-like string literal outside `t()`** — keys are often stored in a map (`HEADLINES = { gallery: 'queue.galleryRunning' }`) and passed to `t()` as a variable, which the `t('…')` regex cannot see; that is how `queue.galleryRunning`/`purging`/`translating` and 24 keys behind `t(cond ? 'a.edit' : 'a.add')` ternaries stayed missing while the audit reported "0 missing". A literal counts as a suspect only when its first segment is a real namespace and it is **not** a prefix of existing keys (`boardGames.statuses` is a `` t(`${ns}.${x}`) `` prefix, not a key). (2) **Interpolation mismatch** — `t('k', { size })` against a text that says `{{bytes}}`; i18next prints the unknown placeholder **as text**, so nothing else catches it. It found 8, including „14 ობოლი ფაილი · {{bytes}}" and five `deleteHint`s that passed `title:` to a `{{name}}` text. ⚠️ **A third check was added on 2026-09-11 (§1.1) and it found six missing texts the audit had been reporting as fine.** A dynamic key's prefix does **not** always end at a dot: `t(`bulkVideo.action_${a}`)` breaks mid-segment, and the old pattern (`.` immediately before `${`) matched nothing at all — so `action_type`, `action_tags_add`, `action_tags_remove` and their three `confirm_*` twins printed raw on `/status` while the audit said „0 missing“. The regex now captures everything up to `${` and compares with a plain `startswith`, which is correct for both shapes. ⚠️ **The convention is now `{{name}}` for every record-name placeholder** (`videos.deleteHint` was the one holdout and was normalised).
- ⚠️ **`frontend/src/lib/layers.ts` is the only place a z-index is decided** (added 2026-09-07 for Tasks §1.1/§1.2). Popups (Radix `Select`, `Popover`, context/action menus, the header dropdown) portal to the end of `<body>`, so they share a stacking context with every modal and only z-index decides who is visible. They all sat at `z-50` while modals moved to `z-60/61`, drawers/lightbox to `z-80/81` and `useConfirm` to `z-90/91` — so **every dropdown opened inside a modal rendered behind it** and read as "the list doesn't open" (notes/bookmarks category+status, game status, video type, board-game genre delete, gallery "no theme"). Popups are therefore `z-[100]` and tooltips `z-[110]`: **above every layer**, because they are opened *from* the topmost one. ⚠️ react-select needs more than a z-index — its menu was also **clipped** by `ModalShell`'s `overflow-y-auto`, so `reactSelectPortal` (`menuPortalTarget` + `menuPosition: 'fixed'` + a `menuPortal` z-index) must be spread into every react-select usage (`GenreSelect`, `TagSelect`, `MovieMultiSelect`). ⚠️ **And that portal needs `pointerEvents: 'auto'` on `menuPortal`** (fixed 2026-09-09, in `lib/selectStyles.ts`): a Radix modal sets `pointer-events: none` on `<body>` while open and only `DialogContent` is clickable, so a menu portaled into `<body>` **inherits** it — the list opens, the keyboard works, and the mouse selects nothing. It read as "you expand the record picker and can't choose anything" and it hit *every* modal (sync, translations, gallery, tag inputs), which is why the fix belongs in the one style object and not in a caller. ⚠️ Tailwind reads class names out of the source, so these strings must stay literal — `` `z-[${n}]` `` generates nothing.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Current state (2026-09-12): **4389 nodes, 9505 edges, 353 communities**. Dated backups of previous graphs sit in `graphify-out/<date>/`.

⚠️ **Invoke it as `python -m graphify <cmd>`.** The bare `graphify` name resolves to an extensionless path Bash cannot execute (`Permission denied`), and `graphify.exe` is blocked by this machine's Application Control policy. `python -m graphify.cli` is the wrong module (exit 255).

Rules:
- For codebase questions, first run `python -m graphify query "<question>"` when graphify-out/graph.json exists. Use `python -m graphify path "<A>" "<B>"` for relationships and `python -m graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `python -m graphify update .` to keep the graph current (AST-only, no API cost). Add `--force` after refactors that delete code, or the rebuild refuses to shrink the graph.
- Known warnings, both harmless: `.sql` files contribute nothing without `tree_sitter_sql` (`backend/mediary_backup.sql`), and community labels drift after a rebuild — `python -m graphify label` refreshes them but **needs an LLM API key, so ask before running it**.
